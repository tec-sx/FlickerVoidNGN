# FlickerVoidNGN

A C# engine built for fast prototyping and easy development.

The target game is a third-person narrative RPG/adventure with an orthographic 2.5D look: 3D scenes with hand-drawn textures and a 2D feel. It is neither 2D-first nor photoreal. Lighting is the most important part of the look. The game is player-paced: no decay timers or forced timings.

Plan, decisions and roadmap: `Docs/Plan.md`.

## Stack

- .NET 10 LTS; NativeAOT for release builds, so runtime libraries set `IsAotCompatible` and avoid reflection (use source generators, such as System.Text.Json source generation).
- Silk.NET for windowing, input and graphics bindings. Vulkan 1.3 only, on Windows and Linux (Direct3D 12 was dropped: Vulkan has the RTX features, and one API halves the graphics code and its tests).
- HLSL shaders, compiled by DXC to SPIR-V. The `ShaderCompiler` tool (`Source/Tools/ShaderCompiler`) wraps DXC for the builder and for tests and depends on nothing; games never compile shaders, they load the builder's `.spv` files through `ShaderLibrary`.
- Arch for entities and components, BepuPhysics for physics, SharpGLTF for glTF.
- Avalonia for the editor, with its GPU interop for the viewport. The editor is four projects in `Source/Editor`: `Shell` (`FlickerVoid.Editor`, the program: AXAML views, the viewport's GPU interop, the material editor window, the project picker and Play), `Core` (`FlickerVoid.Editor.Core`: `EditorScene`, the camera, gizmos, picking, overlays, and the inspector and View tab view models), `Assets` (`FlickerVoid.Editor.Assets`: the asset browser, material documents and unsaved content) and `Persistence` (`FlickerVoid.Editor.Persistence`: project files, building, creating and launching games). Only the shell uses Avalonia, so the others run headless in tests; it maps Avalonia keys and mouse to Core's `ViewportInput` (`ViewportKeys`). The editor follows MVVM: AXAML views with compiled bindings, view models on CommunityToolkit.Mvvm (`[ObservableProperty]` partial properties), and testable models (`EditorCamera`, `EditorScene`) under them. Its viewport draws the world through `SceneRenderer` with editor passes added after post-processing (`SkyPass`, a sky-like gradient where the scene left the view empty and hidden in the game view, then `GridPass`, thin faint lines that only suggest the ground, then `OverlayPass` for gizmos, selection shapes and the icons of lights and other invisible entities, built each frame by `OverlayBuilder`). When the selection is a camera, its live view is drawn in the viewport's bottom right corner, framed (`ViewportViewModel.GetPreviewCamera`; `ViewportRenderer` draws it with a second `SceneRenderer` without the editor passes and copies it in with `ICommandList.CopyTexture`'s destination offset). Picking is on the CPU, so it needs no GPU: icons in screen space first (`EditorIcons`), then model triangles (`ScenePicker`). Editor icons are Material Symbols (Apache-2.0) PNGs in `Source/Editor/Core/Icons` and the editor's shaders are in `Source/Editor/Core/Shaders`; the shell builds them into `Content/Engine/EditorIcons` and `Content/Engine/Editor`. F frames the selection, or the whole scene, keeping the view's direction (`ViewportViewModel.FrameSelected`, `EditorCamera.Frame`); a right-click without a drag opens the viewport's options. The gizmo's move and rotate handles follow the world's axes or the entity's own (`GizmoSpace`; scale handles always follow its own), and it snaps when the viewport toolbar turns it on (`GizmoSnap`): moves put the dragged axis on a grid, turns go in steps of degrees, scaling in steps of the starting scale. Menus are shared controls (`Shell/Controls`): view models offer `MenuChoice`s (Core `Menus`: name, group, icon name from `MaterialIcons.Find`, key, action) and each menu picks its own `MenuGrouping` (none, separators or submenus); Shift+A opens the searchable Add menu (`SearchMenu` over `SearchMenuViewModel`, via `EditorMenus.AddChoices`) over the viewport (`EntityPreset`s), the asset browser (`NewChoices`) and the flow graph, and a right-click opens a plain options menu (`EditorMenus.ShowOptions`, `MenuNode`s through the `ChoiceMenuItem` theme); menus scroll past `EditorMenuMaxHeight`. `SearchBox` is the one search field (rounded, magnifying glass, clear button), bound to whatever it searches. The side panel resizes and splits the scene outliner over the Inspector, View and Data tabs. The scene outliner (`SceneTreeViewModel`) shows folders and entities with icons (`SceneIcons`, by component): an entity's folder is `EntityData.Folder` in the scene file (`folder`, held as the Runtime component `EntityFolder` and saved back); choosing a folder selects everything in it, and the selection holds many entities (`EditorSelection.Entities`, with `Selected` for the inspector and gizmo, which moves the rest with it); folders are created (filing the selection), renamed, removed and dragged into each other there. The shell's look lives in `Themes/EditorTheme.axaml`: Fluent recoloured with a warm dark palette, never flat: the window, bars, headers and tabs are the frame (`EditorFrameBrush`, the kitchen palette's green), and every content area (viewport, trees, lists, forms, the flow canvas) sits in a `Border.well` sunk into it (the darker panel colour, slightly rounded, an inner shadow), with text inputs darker still; compact sizes, icon buttons (Material Icons path data in `MaterialIcons`) coloured by what they do (`play`, `save`, `delete`, `bake`), and the viewport bars; the main window extends into its title bar (`ExtendClientAreaToDecorationsHint`), so the logo, title, tool buttons and Play share one bar with the system's caption buttons, and the empty bar behind them (`WindowDecorationProperties.ElementRole` TitleBar) drags the window; numbers in the inspector are `DragNumberBox`es, dragged sideways or typed after a click, with a bar in the axis colour on X, Y and Z and a yellow one (`EditorValueBrush`) on every other number. Every edit of the editor's world goes through `EditorScene` (`SetComponent`, `AddComponent`, `RemoveComponent`, `AddEntity`, `DuplicateEntity` (Ctrl+D), `DestroyEntity`), which raises `Edited` and leaves the scene unsaved (`IsUnsaved`, `UnsavedChanged`) until it is saved or another scene opens; the inspector, gizmo drags and Bake Probes' file names all use it, and nothing else writes to that world. Material and mood edits are held unsaved by `UnsavedContent`, the `IContentManager` the editor runs on, which serves them to whatever loads through it (the viewport shows them at once) until they are saved or discarded; a file that changes on disk while it has unsaved edits keeps them, and the status bar says so. The title shows `*` while anything is unsaved, and the unsaved assets prompt (`UnsavedAssetsDialog`: Save, Discard, Cancel) lists the scene and the assets before the editor closes, and the scene before another scene opens (`MainWindowViewModel.AskUnsaved`). The Material Editor is its own window (`MaterialEditorWindow`): a browser of the content folder's `.fvmat` files, a field per parameter the scene shader declares (the inspector's field view models over `IEditableValue`), edits held unsaved with Save and Discard, and a sphere or cube preview rendered by `MaterialPreview` on its own device and read back into a bitmap, so it needs no GPU interop. The inspector has no per-component code: it lists the components registered for scene files (`ISceneSpawner.Components`, each a `SceneComponent` with its source-generated `JsonTypeInfo`) and picks a field view model by property type, refined by optional attributes (`[Color]` and `[ContentFile]` from Runtime; `[Range]` from DataAnnotations); string arrays such as `MeshRenderer.Materials` are edited item by item (`ListFieldViewModel`). A string naming a content file (`[ContentFile]`) is picked like Unreal's asset picker (`AssetFieldViewModel`, and each item of such a list, over `AssetPickerViewModel`; `AssetPickerView` in the shell): the current file with its kind's icon opens a popup listing the files with the field's extensions, read again on each opening, with a search box (Enter takes the first match) and None when the value may be empty; the button beside it raises `AssetPickerView.OpenRequestedEvent`, and the main window (for its own fields and the flow editor's) shows the file in the asset browser (`AssetBrowserViewModel.Reveal`) and opens it as a double-click would (`MainWindowViewModel.OpenContentFile`). The View tab beside the inspector edits the viewport's `LightingMood` the same way (`ViewSettingsViewModel`, a field per mood property): the mood file the open scene names (a `SceneMood` component on an entity, from Rendering; the Add menu's Scene Mood), or else a `.fvmood` opened in the asset browser, or else the default mood, unsaved; the viewport draws with that file and the View tab edits it (`MoodDocument`, its edits held by `UnsavedContent` like a material's). The mood includes its `Tonemapper`: post-processing ends with a tonemapper picked by enum (`Uncharted2` Hable filmic by default, `Aces`, `None`) and switched in `Post.hlsl`'s `Tonemap`; a new one is an enum value and a case there. Bake Probes (`SceneProbes`) bakes every irradiance volume with that mood on a device of its own into its probes file in the content folder (a volume without one gets `<Scene>.<Volume>.fvprobes` beside the scene), and the viewport's probe cache reloads it. Save (Ctrl+S) writes the world back into the open scene file (`SceneLoader.Save` over `ISceneSpawner.Capture`): one entity per line, components the world left unchanged kept as the file wrote them and changed ones written in full; comments are lost. Save Assets (Ctrl+Shift+S) and Discard Assets save or drop every unsaved material and mood. The asset browser under the viewport (`AssetBrowserViewModel` over `AssetCatalog`) shows the content folder's tree under its search box, a narrow column of kind filters (by extension) and the selected folder's subfolders and files as tiles (`Items`, an icon and colour per `AssetKind`, `AssetKindLooks`), hidden dot-files skipped; the search looks through everything below the selected folder; it has no buttons: tiles and tree folders have context menus (open, rename, delete, new, import, reimport, up, refresh), and a tile dropped on a folder moves there (`MoveTo`); files from outside the editor, dropped on the browser or picked with Import, are copied into the folder they land on or the selected one (`Import`), their sources remembered in the content folder's hidden `.imports` file (`ImportSources`, kept through renames, moves and deletes; the builder skips hidden files), so Reimport copies a changed source again; opening a scene replaces the open one (`EditorScene.Open`, `SceneLoader.Unload`), opening a material shows it in the material editor, and a model dragged into the viewport becomes a mesh entity named after it, on the mesh or ground under the mouse (`AssetDrag`, `ViewportViewModel.DropModel`). It creates folders, scenes, materials and moods (named `New Scene` and so on, numbered when taken, naming the content folder's schema), and renames and deletes files and folders, all through `IContentManager` (`Write`, `CreateFolder`, `Move`, `Delete`). With a project open it also shows the project's `Source` folder as a second root, Code (`AssetCatalog.ForCode`, paths under `/Code`, build output skipped, `.cs` files opened in the IDE), where it only writes: New > Flow > Flow Node asks for a name and a code folder (`FlowNodePrompt`: the selected code folder, or the one whose path ends most like the selected content folder's, or the first holding a C# project) and `FlowNodeSource` writes the class there in its project's namespace and adds it to the project's JSON context; it is in flow graphs after the next build. Data assets open in the Data tab (`DataDocument` over `DataTypes.ReadAsset`/`WriteAsset`, edits held by `UnsavedContent`): a form generated from the asset's metadata (`DataObjectViewModel`: a field per value, a section per nested object, and a `DataListViewModel` per list of objects such as fragments, whose Add offers each `$type` registered for the element type); the browser's New Data Asset and New Table submenus list the registered types (`AssetChoice`). Tables open there too (`TableDocument`, `TableViewModel`): a form per row, rows added, renamed and removed, and CSV export and import for spreadsheets (`TableCsv`: a `name` column, then one per property, strings as written and other values as JSON). Every save goes through `IContentManager.Write`, which in a development build also writes the source file the build manifest maps it to, so editor changes outlive the next build.
- One codebase for Windows and Linux. When something is OS-specific, build it for Windows first and leave a `// TODO(Linux): ...` note on the Linux side.

## Layout

- `Source/Engine/<Module>/FlickerVoid.Engine.<Module>.csproj`, `Source/Editor/<Module>/FlickerVoid.Editor.<Module>.csproj` and `Source/Tools/<Module>/FlickerVoid.Tools.<Module>.csproj`, tests in the same folders under `Tests/` (`FlickerVoid.Engine.<Module>.Tests.csproj` and so on). Namespaces follow folders.
- Inside a module, folders group by what code is about: Graphics and Graphics.Vulkan by resource kind (`Devices`, `Buffers`, `Textures`, `Samplers`, `Pipelines`, `Commands`, `Presentation`, `Resources`/`Descriptors`); Rendering by feature (`Cameras`, `Meshes`, `Materials`, `Lighting`, `Shadows`, `GlobalIllumination`, `PostProcessing`, `Outlines`, `Extraction`, `Pipeline`); Runtime and Platform likewise (`Loop`, `Windowing`, `Native`).
- Rendering never reads the Arch world while drawing: an `IRenderExtractor` (default `WorldExtractor`) copies it into a plain `RenderScene`, then `SceneRenderer` runs its `RenderPipeline` of `IRenderPass`es (Prepare all, write the frame data, Execute all) over a shared `RenderContext`. New rendering features are new passes added, inserted or replaced in the pipeline, not branches in `SceneRenderer`. The last default pass is `OutlinePass`, like Unreal's custom depth stencil outlines: meshes whose entity has an `outline` component (`Outline`, a color) are drawn as silhouettes in their color into a mask, then a line `Width` pixels wide (2 by default) is drawn around them over the output, seen through whatever stands in front.
- Engine file types carry `fv` extensions: scenes `.fvscene`, materials `.fvmat`, lighting moods `.fvmood`, canvases `.fvcanvas`, texture settings `.fvtexture`, shader descriptions `.fvshader` (built shader parameters `.fvparams`), baked models `.fvmodel`, baked probes `.fvprobes`, entity templates `.fventity`, data assets `.fvdata`, data tables `.fvtable`, flow graphs `.fvflow`, projects `.fvproject`. Text ones are JSON with a `$schema`; standard formats keep theirs (`.glb`, `.png`, `.hlsl`, `.dds`, `.spv`).
- Content is built by the `Builder` tool (`Source/Tools/Builder`, `FlickerVoid.Tools.Builder`), a command-line program the editor runs too. A game lists its source folders as `<FlickerVoidContent Include="Content" />`, and `Source/Tools/Builder/FlickerVoid.Tools.Builder.targets` (imported by `Samples/Directory.Build.targets`) builds them into `Content/` in the output and publish folders. The shaders of the engine modules a project references (`Source/Engine/<Module>/Shaders`) are built into `Content/Engine/<Module>`, where `ShaderLibrary.ForEngine` finds them, so test projects that draw import the targets too. A shader is `Name.hlsl` plus `Name.fvshader` listing its entry points and stages, built into `Name.EntryPoint.spv`; HLSL uses real `#include`s. Images (PNG, JPEG, TGA, BMP) become sRGB `Name.dds` files with full mip chains (`DdsImage`), as their optional settings beside them say (`Paper.png.fvtexture`, `TextureSettings`: BC7 or uncompressed, a size limit the image is halved to, tint, crop; applied by `TextureEdits`, read by `TextureImporter` as a dependency, and listed by the asset browser as part of the image, moved and deleted with it); content names a texture by its source image (`Paper.png`) and `TextureLibrary` loads the `.dds`. Everything is painted on a canvas: a mood names a `.fvcanvas` (`CanvasFile`: image, tiling up the screen, tint, grain, curvature), which `PostProcessPass` wraps around the camera like a sky (`CanvasView`) and shows unlit where nothing is painted and through paint that is not thick impasto. Double-clicking an image or a canvas in the asset browser opens the texture editor (`TextureEditorWindow` over `TextureEditorViewModel`: a field per setting, held unsaved by `UnsavedContent`, and a CPU preview of what the build makes of the image or of the canvas repeated by its tiling). A shader may declare material parameters in its `.fvshader` (`parameters`: name, `float` or `color`, default, optional limits), written to `Name.fvparams`; `Name.fvmat` files set them by name (`MeshRenderer.Materials`, one per mesh part), and `MaterialLayout` packs them tightly in declared order for the shader's `LoadMaterial`. glTF models (`.glb`, `.gltf` with its buffers and images) are baked by `ModelImporter` into `Name.fvmodel` (`ModelFile`: mesh parts, BC7 textures, baked animation clips); content names them by source (`Room.glb`) and `MeshLibrary` loads the `.fvmodel`, so the runtime never reads glTF or decodes images. Each file goes through the `IAssetImporter` registered for its extension, or is copied; a content-hash cache (`.build-cache.json`) skips files whose source, dependencies and importer version haven't changed.
- Entity templates (`.fventity`, `EntityTemplates`, `SceneLoader.Templates` and a game service) are an entity's components and values, optionally over a `base` template, like a Blueprint carrying looks and data. A scene entity names one with `template` and keeps only what differs from it: `SceneLoader` expands templates before spawning or patching (`JsonMerge.Merge`, property by property) and saves only the differences (`JsonMerge.Diff`); a template that changes on disk patches every loaded scene using it. Game code spawns one with `EntityTemplates.Spawn`, placed at a transform and started.
- Data assets (`.fvdata`: one object, like an Unreal Data Asset with instanced objects) and data tables (`.fvtable`: named rows of one type, like a Data Table) hold C# types registered on `Game.Data` (`DataTypes`): modules add the source-generated context describing their types (`AddResolver`), then `Register<T>(name)` for asset types, `RegisterRow<T>(name)` for row types and `RegisterDerived<TBase, TDerived>(name)` for fragments, conditions and effects. A file names its type in `type`; a polymorphic value names its derived type in `$type`, added through a resolver modifier, so reading stays reflection-free. `DataAssets` (a game service from `SceneHost`) loads them, one object per file until it changes on disk, lists every asset of a type (`LoadAll<T>`) and finds a definition by its tag id (`Find<T>`), and the `data` and `table` schemas list every registered type. References to data files are content paths (`[ContentFile(".fvdata")]`).
- Input is read as actions, like Enhanced Input: an input map (`InputMap`, a data asset of type `inputMap`, registered by `game.AddInput()`) names each action by a tag and binds keys, mouse buttons or the mouse's movement, each adding its `Value` (so W, A, S and D make a move vector). `InputActions` (a frame system and service, added by `SceneHost` before the game's systems, with an empty map until the game sets one) gives each action's value and whether it is held, pressed or released, and sends `InputActionEvent`s; systems read actions by tag, never keys. `GestureTracker` follows a press, hold, mash, hover or automatic `Gesture` of one action.
- Characters are point and click (owner, 2026-11-21: point and click with the orthographic view; no third-person camera). The `Characters` module (over Physics) has `CharacterMover` (scene component `characterMover`: speed, turn speed, arrive distance) and `CharacterMovementSystem` (`game.AddCharacters()`, after `AddPhysics` when the game has physics): a `MoveCommand` event sends a character walking to a point (a `Destination` component while it walks), it walks straight there turning to face its way (characters face +Z, the front of a glTF model) and standing on the ground a physics ray finds, and sends `ArrivedEvent`; `StopCommand` stops it. A `SteerCommand` steers it along a direction instead (a `Heading` component while it walks; speed scales with the direction's length, at most 1, and a zero direction stops it); steering, walking to a point and turning in place replace each other. Paths around obstacles come from the `Ai` module (over Characters, on DotRecast; `game.AddAi(settings)` after `AddCharacters`): `PathSystem` (a service and the movement system's `IPathFinder`) builds a navigation mesh (`NavigationMesh`, one Recast tile, agent radius, height, climb and slope from `NavigationSettings`) from the boxes around every static body (`StaticGeometry`), again when static bodies come or go, and a `MoveCommand` then walks its corners one by one; a point off the mesh is reached as near as the mesh allows, and a move with no way there stops the character. `PathSystem.TryFindRandomPoint` picks a point of the ground within a radius (Detour, with a given `Random`). `FaceCommand` turns a character in place (a `Facing` component while it turns). Perception (`Ai/Senses`, ported from the Unreal AI controller's sight and hearing; no damage sense, as there is little combat): a `perception` component (sight radius, lose-sight radius, sight angle either side of +Z, eye height, hearing range, memory) sees `perceivable` entities, and `PerceptionSystem` (a fixed system and service, `GetSeen`, `GetHeard`) sends `TargetSeenEvent` and `TargetLostEvent` as they come into view within the sight radius with no body in between (`IPhysicsSystem.RayCast` can ignore the perceiver's own body) and leave it past the lose-sight radius, and hears a `NoiseEvent` within its hearing range times the loudness and the noise's range (`NoiseHeardEvent`), remembering it for its memory (`NoiseForgottenEvent`). A click becomes a world ray with `CameraView.GetRay` (Rendering, over `Ray.FromViewProjection` in Runtime's `Geometry`, which the editor's picking shares) and meets the world through `IPhysicsSystem.RayCast`, which returns the nearest body's entity, point and normal.
- Interaction (the `Interaction` module over Platform, ported from FVInteractionSystem for point and click; `game.AddInteraction()`) lets interactors use interactables. An `interactable` component names an `InteractableDefinition` data asset (type `interactable`: up to three `InteractionOffer`s, each an input tag, an action tag, a `Gesture`, display, conditions, effects, weight and uses; a cooldown; the interactor kinds it accepts), loaded from `DataAssets` when the entity activates into an `ActiveInteractable` (state, uses left, cooldown left). An `interactor` (kind, reach) is focused on one with `FocusCommand` (the one under the mouse); `InteractionSystem.GetOffers` lists the focus's offers for prompts; `InteractionInput` presses or releases an input, and a press within reach starts the heaviest offer for it that can be done (offers may share an input: a door's Use unlocks it while locked and opens it after), followed by a `GestureTracker` until it succeeds or ends (`InteractionEnd`). A success sends `InteractionActionEvent`, uses the offer up (every offer used up completes the interactable, else it rests for its cooldown) and applies its effects with the interactor as instigator and the interactable as target. Responses handle the action event: a `lock` (`Lockable`, locked by the action it names, with key and pick settings; the `locked` condition reads it) and a `toggle` (opened and closed by its action, blocked while locked, `ToggledEvent`, `ToggleBlockedEvent`); the `interactorTags` condition checks the interactor's `OwnedTags`. Walking to what was clicked is the game's controller's job, over `Characters`: the demo project's `ClickControlSystem` (`Gameplay/Protagonist/Control`) turns a press of `Input.Use` into a ray from the camera, walks the `protagonist` there, or focuses the interactable it hit, walks within reach and presses Use (and ignores clicks while the protagonist is in a conversation), its `WalkControlSystem` turns the `Input.Move` action (WASD) into a `SteerCommand` on the ground relative to the camera, held still during a conversation, its `InteractableHighlightSystem` outlines the interactables the protagonist's interactor could use within its `interactableHighlight` range (`InteractableHighlight`: range, color) and takes the outline off the rest, and its `DoorSwingSystem` (`Gameplay/World/Objects/Doors`) swings a `doorSwing` door about its hinge as its toggle changes and rattles it when locked (a `NoiseEvent` from whoever tried it); its `KeySystem` (`Gameplay/Protagonist/Resources/Possessions`) hears a toggle blocked by a lock first and, when whoever was blocked carries an item with the lock's `Key` tag, unlocks it (taking the key when the lock consumes it) and lets the toggle go ahead. The demo scene has a cellar key pickup the fox takes before the door opens. Residents (`Gameplay/World/Society/Residents`, in place of the Unreal StateTree AI): a `resident` (wander radius, rest) is run by `ResidentSystem`, which faces whom it talks to, stops to watch whom it sees until it loses sight of them, turns toward noises it hears, and otherwise walks to random points within its wander radius of home, resting between walks; the innkeeper watches the fox and turns at the rattling door. A physics collider's `Offset` places its shape in the entity's space (a door's panel beside its hinge). Conditions and effects read the game's facts, `Game.Facts` (an `IFactDatabase` service).
- Maps (the `Maps` module over Runtime, ported from FVNavigationSystem; `game.AddMaps(settings)`) know where things are. A `MapDefinition` (type `map`: priority, `AvailableWhen` conditions, layers) has `MapLayer`s (name, image, `Min` and `Max` corners on X and Z, optional height limits; `WorldToUv` and `UvToWorld`, with north at -Z and east at +X); `MapSystem` (a fixed system and service over every map of the content folder, `DataAssets.LoadAll`) finds the map and layer under the `navigator` (minimap radius, compass field of view, hidden marker categories), sending `ActiveMapChangedEvent`. Markers are `MarkerDefinition`s (type `marker`: icon, priority, `VisibleWhen`, fragments `minimap`, `compass`, `worldMap` and `discovery`), placed by a `mapMarker` component on an entity or by `AddMarker` at a point (`MarkerHandle`); visibility follows their conditions on every fact change, a `discovery` marker is discovered within its radius (its fact set, `OnDiscovered` applied), and one marker can be tracked and one waypoint placed (`MapSettings.WaypointMarker`). Views are plain data built on request: `BuildMinimapView` (markers within the radius around the navigator, turned against the view's heading, clamped to the edge when the marker says so), `BuildCompassView` (headings in degrees clockwise from north, within the field of view, with elevation above or below) and `BuildWorldMapView` (a layer's markers as uvs). The marker events (`MarkerAddedEvent`, `MarkerRemovedEvent`, `MarkerDiscoveredEvent`, `MarkerVisibilityChangedEvent`, `TrackedMarkerChangedEvent`, `WaypointChangedEvent`) tell the interface what changed. The demo's HUD minimap draws the minimap view's markers (the tracked one as a diamond); `Maps/Inn.fvdata` covers the inn, the innkeeper is a `Person` marker and the cellar door an `Objective` shown while the cellar quest is active.
- Inventory (the `Inventory` module over Runtime, ported from FVInventorySystem; `game.AddInventory(settings)`) carries items. An `ItemDefinition` data asset (type `item`: category, weight, cells across and down, stack size where 0 is unlimited and 1 makes every unit its own entry, quest item, and fragments such as `usable` (use conditions, effects, consumed on use), `charges` (uses per unit) and `value`) is held in `ItemStack`s (id, item, quantity, immutable `ItemInstanceData` records such as `ChargesLeft` and `Stolen`; stacks with data never merge). An `inventory` component names its starting items and money and whether carry limits apply (off for chests and shops); while playing it is an `ActiveInventory`. `InventorySystem` (a service) does the rest: weight and cell limits from `InventorySettings` plus the bonus the game grants (units fill existing stacks for free, each new stack claims the item's cells, key item categories take neither), story items that ignore limits, removal from plain stacks first, use with the owner as instigator and target (a charge first, so a partly used unit becomes its own stack), transfers (plain units move as far as they fit, stacks with data whole; optionally marked stolen), `Receive` for what is picked up, money, and finding items by tag. Changes are sent as `ItemChangedEvent`, `StackChangedEvent`, `ItemUsedEvent`, `MoneyChangedEvent` and `CapacityChangedEvent`. A `pickup` component (item, quantity, destroyed when empty) is an `ActivePickup` stack while playing; `PickupSystem` (a service) takes it into a picker's inventory as far as it fits or uses it where it lies (`PickedUpEvent`, `UsedInPlaceEvent`, after which an empty pickup goes). The inventory conditions (`hasItem`, `hasItemWithTag`, `hasMoney`) and effects (`giveItem`, ignoring limits, `takeItem`, `giveMoney`, `takeMoney`) look at their `Subject`, the instigator by default, and find `InventorySystem` and `DataAssets` in the context's services; `pickUp` and `useInPlace` are effects for an interaction offer, with the interactor picking up or using the interactable, so Inventory needs no Interaction. Outfits: an `equipment` component (starting items by slot, linked to carried stacks, and whether only carried items can be worn) is an `ActiveEquipment` while playing, and `EquipmentSystem` (a service) wears `equippable` items (slots, blocked slots, granted tags, equip conditions, mesh) one per slot, taking off what conflicts; worn items' granted tags are added to the wearer's `OwnedTags` (keeping tags others gave), a worn stack that leaves the inventory comes off (`EquipmentChangedEvent`), and worn `container`s (bags) add cells and weight allowance. `InventorySystem` reads `ActiveEquipment` for that: worn stacks are removed and used last, never transferred, and a worn bag stays on while its room is needed. The `isWearing` condition checks an item or a granted tag, and `giveItem` can wear what it gives. Loot: a `LootTableDefinition` (type `lootTable`: up to three entries, each an item or a nested table with a quantity range, a chance and conditions, plus a money range) is rolled by `LootSystem` (a service, with the `Random` given to `AddInventory` so tests seed it; nested tables roll their quantity of times, at most eight deep, and a table leading back to itself is skipped), into an inventory as far as it fits (`GiveLoot`, the `giveLoot` effect), or once into a `lootable` container (table, owner, rolled). Inside the engine the `Inventory` component's name meets the `FlickerVoid.Engine.Inventory` namespace, so engine code outside its folder names it `Inventories.Inventory`.
- Attributes (the `Attributes` module over Runtime, ported from FVAttributeSystem in place of GAS attribute sets; `game.AddAttributes(random)`) are numbers on entities named by tag (`Attribute.Skill.Stealth`). An `AttributeDefinition` data asset (type `attribute`, its id the attribute's tag: category, min, max, integer) clamps and rounds the attribute; one without a file is unclamped. An `attributes` component (`AttributeSet`: starting base values) is an `ActiveAttributeSet` while playing, and `AttributeSystem` (a service) reads current and base values, sets and adds to base values, and applies and removes modifiers (`ModifierDefinition`, type `modifier`, in place of Gameplay Effects: changes that `Add`, `Multiply` or `Override` an attribute's current value, as (base + adds) x multipliers unless overridden, then clamped, and granted tags added to `OwnedTags` through `GrantedTags.Replace`, which equipment uses too; they last until removed, as the game is player-paced), sending `AttributeChangedEvent`. Checks (`CheckDefinition`, type `check`: an attribute, a `CheckRoll` of none, 2d6, d10 or d20, and bonuses with conditions) are rolled, previewed and given a success chance by `CheckSystem` (a service, with the seeded `Random`) for the context's instigator. Rules: the `attribute` and `passiveCheck` conditions, and the `modifyAttribute`, `setAttribute`, `applyModifier` and `removeModifier` effects, on their `Subject` (the instigator by default).
- Abilities (the `Abilities` module over Attributes, ported from the Gameplay Ability System setup of FVGameplay; `game.AddAbilities()` after `AddAttributes`) are what entities can do. An `AbilityDefinition` (type `ability`: id and tags; `AbilityPolicy` `OnInput`, `WhileInputHeld` or `OnGranted`; `AbilityGroup` `Independent`, `ExclusiveReplace` or `ExclusiveBlock`; required and blocked owner tags; tags of abilities it blocks while running and cancels when it starts; owned tags while running; conditions; `AbilityCost`s such as `attributeCost`; `OnActivated` effects with the owner as instigator and its target as target; `Instant` to end at once; failure messages by reason) is granted through `abilitySet`s (abilities with their input tags, and modifiers applied while granted) that an `abilities` component lists (`GrantedAbilities`, with an optional `abilityTagRelationships` file adding blocks, cancels and requirements to every ability with a tag, like Lyra's tag relationship map). `AbilitySystem` (a service) activates abilities by input (`InputPressed`, `InputReleased`), by tag (`TryActivate` on a target) or as granted, checks in order whether it is active, blocked, missing or holding tags, held off by an exclusive group, failing conditions or unable to pay (`AbilityFailure` tags, `AbilityFailedEvent` with the message), and sends `AbilityActivatedEvent` and `AbilityEndedEvent`; behaviour beyond effects is a system that handles the activated event and calls `End`. The `activateAbility` effect and `canActivateAbility` condition let offers and rules use abilities, so Abilities needs no Interaction.
- Flow graphs (`.fvflow`, the `Flow` module over Runtime, like the Unreal Flow plugin) are scripted sequences for story, quests and dialogue: nodes linked output pin to input pin. A node derives from `FlowNode<TOut>` (one input, `In`) or `FlowNode<TIn, TOut>`, whose enums are its pins (`FlowInput`, `FlowOutput`, `NoPins`, or its own nested `Out`), so it triggers `context.Trigger(Out.True)` with no pin strings; files name pins by enum name, and a `FlowRun` resolves the links to pin indices once, throwing for a missing node or pin. Each node type is registered on `Game.Data` with `RegisterDerived<FlowNode, T>` and named by `$type`; nodes without inputs run as the run starts. A game project's nodes are classes marked `[FlowNodeType("name")]`, registered by the `FlowNodeTypes.Register(game.Data)` that the `Generators` tool (`Source/Tools/Generators`, a Roslyn source generator referenced as an analyzer) writes into the project, beside its JSON context (`AddResolver`), which lists each node with `[JsonSerializable]` because System.Text.Json's generator can't see another generator's output. The editor opens a `.fvflow` from the asset browser (New Flow creates one with a start node) in a `FlowEditorWindow`: an endless canvas (`FlowCanvasView`: right or middle drag pans, the wheel zooms about the mouse, F frames the selected node or all, and it opens framed; `FlowGrid` draws faint lines under it) over `FlowGraphViewModel` (Core: nodes laid out in fixed rows so pins sit where `FlowPinViewModel.Point` says, wires drawn by `FlowWires`; Shift+A adds a node of any registered type, grouped by module, right-click offers options, drag nodes, drag from a pin (grabbed within `GrabRadius`) and drop on or near a node to wire it to its nearest fitting pin (`FindDropTarget`, the wire snaps while dragging), drop a wire on empty space to add a node wired to it (`GetAddChoices`), Delete removes) beside the selected node's form (`DataObjectViewModel`, its id and place hidden); edits are held by `UnsavedContent` through `FlowDocument` and written with `FlowGraphs.Write`. `SceneHost` adds flow to every game and serves `FlowGraphs`. `game.AddFlow()` registers the core nodes (`start`, `finish`, `branch`, `applyEffects`, `waitForConditions`) and the `flow` schema; `FlowGraphs` reads a file and starts a `FlowRun` against a `ConditionContext`. Nodes are shared data: a run keeps the active nodes, passes signals along links in order, tells active nodes when a fact changes, and stops a trigger that loops. Gameplay's condition and effect types (`fact`, `group`) are registered by `Game` itself, so any data file can hold condition sets and effect lists.
- Story (the `Story` module over Flow, ported from FVStorySystem; `game.AddStory()`) is quests and knowledge kept in facts, so saves hold them. A quest (`QuestDefinition`, type `quest`) keeps its `QuestState` in the fact its id names: it starts by `AutoStartWhen` or a rule, fails by `FailWhen`, completes when its required objectives are done (each `QuestObjective` sets its fact to 1 when visible and `CompleteWhen` passes; a quest with none is completed only by a rule), applies `OnStarted`, `OnCompleted` or `OnFailed`, and runs its `.fvflow` while active. `QuestSystem` (a fixed system and service) follows every quest of the content folder (`DataAssets.LoadAll`), evaluates them on each fact change (re-entrant, at most `MaxPasses`), starts with the game's first step and sends `QuestChangedEvent`. Knowledge (`KnowledgeDefinition`, type `knowledge`: a `KnowledgeKind`, prerequisite ids and `OnLearned`) is learned through `KnowledgeSystem` (a service), which sets its fact to 1. Rules name quests and knowledge by id: the `questState` and `knows` conditions read the facts, the `setQuestState` and `learn` effects go through the services, and the flow nodes `setQuestState`, `completeObjective` and `waitForQuestState` drive quests from graphs.
- Dialogue (the `Dialogue` module over Flow, ported from FVDialogueSystem; `game.AddDialogue()`) runs one conversation at a time on flow graphs. A `dialogueParticipant` (`Speaker`, the character id lines name; `Dialogue`, its `.fvflow`) is someone to talk to; `DialogueSystem` (a fixed system and service) starts the owner's graph with the instigator as the run's instigator and the owner as its target (`Start`, or the `startConversation` effect a Talk offer applies), and talks to the interface through events (`ConversationStartedEvent`, `LineStartedEvent`, `LineFinishedEvent`, `ChoicesPresentedEvent`, `ConversationEndedEvent`, `BarkEvent`), which answers with `Advance`, `Choose` and `End` (also the player's way to leave). The `line` node shows a line (speaker resolved to an entity, duration from `DialogueSettings` when it has none, or waiting for input), the `choice` node offers at most three options (`First`, `Second`, `Third`), hidden or shown locked by their conditions' failure presentation, and the `bark` node says a fitting row of a `bark` table (identity, required and blocking tags, conditions), not the speaker's last. The conversation ends when its graph finishes or has nothing left to do, when it is ended, or when its owner is gone. There is no audio yet, so lines carry no voice.
- Saves (`Runtime/Saves`, ported from FVStorySystem's save subsystem; `SceneHost` adds them to every game, in `FlickerVoid/<title>/Saves` under the user's local application data unless `--saves` names a folder) write slots as `.fvsave` JSON (`SaveGame`: `SaveMetadata` with version, slot, time, play time and checkpoint; the facts; `Entities`, the state of each `saveable` entity by its id; `Destroyed`, the ids of saveable entities that were gone; `States`, game-wide state by key). What is saved is registered on `Game.SaveStates` by the modules, like data types on `Game.Data`: `AddComponent<T>` keeps a plain component as it is through its `JsonTypeInfo` (set back on load, removed from an entity that had none), `Add<TState>` keeps a module's own state of each saveable entity (an interactable's uses, a scannable scanned) and `AddGlobal<TState>` keeps game-wide state, both written with `Game.Data`'s options (so their types need a resolver added there, and polymorphic values such as item instance data, registered with `RegisterDerived`, work), read back in the order added; definitions are saved by their files (`DataAssets.TryGetPath`); entities without a `Saveable` id (placed in the scene with one unique there, like Unreal's save ids) are not saved, and entity references are never saved. Saved: transforms (Runtime), walking and turning (`destination`, `facing`), locks, toggles and interactables, inventories (stacks with their ids and instance data, money), worn items (re-worn, so granted tags follow), pickups and lootables, attributes (base values, and modifiers with their handles), map markers' discovery and the waypoint and tracked marker, and in the demo project door hinges and scans. `DialogueSystem` holds `Save.Block.Dialogue` while a conversation runs and ends any conversation when a save loads. `SaveSystem` (a service) saves, loads, deletes and lists slots (newest first), keeps play time across loads, refuses to save while a block tag is held (`AddBlock`), restores the facts, then the states (destroying saveable entities that were gone), then raises `Loaded`; a missing, broken or newer save loads nothing. Quests come back with the facts, and `QuestSystem` restarts the flows of the active ones on `Loaded`. The demo launcher quick saves to the `Quick` slot with `Input.QuickSave` (F5) and loads it with `Input.QuickLoad` (F9) (`QuickSaves`). The stage 7 gate is the project's `StoryLoopTests` (`Tests/Gameplay/Story`), which load the source `Main.fvscene` headless and play the cellar key quest through clicks and choices, with a save and load in the middle.
- The demo project's story: the protagonist is the `Player` of `QuestSystem` and `KnowledgeSystem` while it is active (`GameplayModule`), the innkeeper in `Main.fvscene` has a Talk offer (`Interactables/Talk.fvdata`, `startConversation`) and the dialogue `Dialogues/Innkeeper.fvflow`, which gives the cellar key quest (`Quests/Cellar.fvdata`) and a topic (`Knowledge/Cellar.fvdata`). The launcher's debug interface (`--debug` or F1) also has a Story panel (`StoryWindow`: the line, the choices to pick, quests and knowledge).
- The demo project's rules: the fox has skills (Perception, Stealth, Charisma) and physical attributes (Health, Intoxication) in `Main.fvscene` and the `Abilities/Protagonist.fvdata` set with `Ability.Lockpick` (needs an `Item.Lockpick`). Its `LockpickSystem` (`Gameplay/World/Objects/Doors`, beside the door) hears a toggle blocked by a pickable lock that no key opened (after `KeySystem`), activates the ability on the door and rolls `Checks/Lockpick.fvdata` (Perception, 2d6, +1 unless `Status.Drunk`) against 4 plus a tenth of the lock's difficulty; success opens it like a key (`DoorLocks.Unlock`), failure cancels the ability, and `LockpickedEvent` carries the result. A mug of ale on a crate (`Items/Ale.fvdata`, drunk where it stands) adds Intoxication and the `Drunk` modifier. The launcher's debug interface has a Rules panel (`RulesWindow`: attributes with their bases, modifiers, abilities and the last check).
- The demo project's scanner (`Gameplay/Protagonist/Resources/Knowledge/Scanning`, ported from the Unreal scanner for point and click): a `scanner` (range, eye height, line of sight, update interval) on the protagonist and `scannable`s (a `ScanDefinition` data asset, type `scan`: display, category, scan duration, `ScannableWhen`, up to three shown `ScanEntry`s each with `VisibleWhen`, `OnScanned` applied on the first completed scan; and the height the scanner looks at). `ScannerSystem` (a fixed system and service, added where there is a window, as it focuses through `PointerPicker`) turns scan mode on and off with `Input.ScanMode` (F), reveals the scannables within range whose conditions pass, focuses the revealed one under the pointer when the scanner sees it, and scans it while `Input.Scan` (the right button) is held (`ScanModeChangedEvent`, `ScanRevealChangedEvent`, `ScanFocusChangedEvent`, `ScannedEvent`). Scan mode does not slow time (the game is player-paced) and revealed scannables are not yet highlighted in the world. The HUD's scan card (`ScanCardViewModel`) takes the prompt's place in scan mode: the focus's title and progress, then its visible entries. The door, the innkeeper and the ale have scans (`Scans/`).
- The game's interface (the `Ui` module over Hosting; owner, 2026-11-21: Avalonia drawn into the game) is Avalonia controls, AXAML and MVVM like the editor, on Avalonia's headless platform with Skia (`UiPlatform.Start<TApplication>()` once, with the game's application holding its styles): a `UiSurface` holds the controls in a window never shown on screen, is handed the window's mouse, keys and typed text each frame and draws them into memory, transparent where there are no controls (premultiplied RGBA). `GameUi` (an `IFrameOverlay`) follows the window's size and draws the surface over the scene each frame (`UiRenderer`: the pixels go through an upload buffer into a texture per frame slot, and `Shaders/GameUi.hlsl` blends them over the target, made linear on an sRGB target). Stages (owner, 2026-11-21: 3D in the interface, reused for inspect) are small scenes shown in the interface: a `Stage` loads its `.fvscene` (models, lights, a camera, a `SceneMood`) into a world of its own, spins its `turntable`s (`Turntable`: speed, drag speed; `TurntableSystem` spins them in the game's world too) and animates its meshes, and while a `StageView` control shows it renders it with a `SceneRenderer` of its own on the game's device and reads it back into a bitmap; dragging across the view turns it. `game.AddTurntables()` registers the component (in a game module, so the editor knows it) and `game.AddStages(device, content)` adds `StageSystem`, which creates and updates them. Post-processing writes coverage into alpha (0 where nothing was drawn), so a stage shows over the interface. Several overlays draw as one through `FrameOverlays` (Hosting), the debug interface last. Overlays that are `IPointerCapture`s (`GameUi` over a control, `DebugUi` when it wants the mouse) are added to `InputActions.PointerCaptures`, and while one captures the pointer, button bindings read as up, so a click on the interface never reaches the world.
- The demo project's interface (`Source/Interface`, `FlickerVoid.Interface`: `InterfaceApplication` with Fluent and `Themes/GameTheme.axaml`, AXAML views over CommunityToolkit.Mvvm view models of the game's services) is drawn by the launcher's `GameUi` under the debug interface (`FrameOverlays`). `GameInterface` (a frame system) owns the HUD (`HudViewModel`, `HudView`): the quest tracker at the top left (`QuestTrackerViewModel`: up to three active quests, the latest changed first, each with its first visible objective not done), the dialogue box at the bottom centre while talking (`DialogueBoxViewModel`: speaker, line, Next, the numbered choices with locked reasons, Leave), and otherwise the prompt for the interactable under the pointer (`InteractionPromptViewModel` over `InteractionSystem.GetOffers(interactor, target)`; the pointer is found by `PointerPicker`, the game service `ClickControlSystem` picks with). Only the dialogue box takes clicks. The look is white and tintable (owner, 2026-11-21: serious, white, tint set in the engine): `HudTint` and the brushes in `GameTheme.axaml`, `HudFrame` panels (`Controls/HudFrame.cs`: a chamfered outline with corner ticks), headings in Glitch Goblin and text in Rajdhani (SIL OFL only; licences beside the fonts in `Assets/Fonts`), and the minimap at the bottom right (`MinimapViewModel`: the compass ring turned against the camera's heading, a tiled map grid moving under the player, the view cone turned by the player's facing, and the markers of `MapSystem.BuildMinimapView`; images in `Assets/Images`). The hub (`HubViewModel`, `HubView`, over the HUD, which hides while it is open) replicates the Unreal hub: a yellow bar with the skewed `FadingStrips` (an opacity mask), the page tabs and Close, and the selected page; `Input.Hub` (Tab) and Close toggle it (Escape still closes the game's window, in `SceneRenderSystem`), `Input.NextPage` (E) and `Input.PreviousPage` (Q) switch pages in a ring, and it reopens on the page last shown. Its dark background takes every click. Its three pages (`HubPageViewModel`: filled from the protagonist when shown, refreshed by their events while shown) are Inventory (`InventoryPageViewModel`: weight and money, a four-column grid of the carried stacks filled up to the inventory's cells, the selected stack with Use and Wear or Take off, and the outfit slots in two columns, `OutfitSlots`; clicking a slot wears the selected stack there when it fits, else selects what is worn there; the protagonist turning on its stage in the middle, `Stages/Protagonist.fvscene`), Character (attributes, the modifiers on them, abilities) and Journal (active quests with their visible objectives, finished quests, knowledge). `DisplayNames` gives the names shown for tags and definitions without a display name.
- Content hot-reloads: `ContentWatcher` (a frame system) reports files that changed on disk to `IContentManager.NotifyChanged`, which forgets the cached JSON and raises `Changed` with the full path. Anything that caches what it loaded from a file (the mesh, texture and probe caches, `SceneLoader`, `LightingMoodDirector`) listens to `Changed` and drops or patches what it holds; the scene loader and mood director keep the last good version when an edited text file can't be read. In a development build the targets also write `Content/.content-build` (the builder and the source folders) and copy the build caches beside it; `ContentWatcher` then starts the builder in watch mode (`ContentBuildProcess`, `--watch`), so saving a source file rebuilds it into the game's content folder and the reload follows. Published games have neither file. Text content has JSON Schemas generated from the same source-generated metadata that reads it (`JsonSchemas`): modules add theirs to `Game.Schemas` (`scene` from every registered component, `mood` from Rendering), and a development run writes them into each source content folder's `.schemas` (`ContentWatcher`), which the builder skips. Content files name theirs with `"$schema": "../.schemas/scene.schema.json"`; root file types carry a `Schema` property for it.
- Modules arrive with their roadmap stage (`Docs/Plan.md`). Don't create empty projects, folders or classes ahead of their stage.

## Porting from Unreal

- Read the Unreal source (FVFramework, FVGameplay and the plugins) before porting, and port its behaviour and its tests. Never write an API from memory.
- C# types drop the Unreal prefixes (`EFVCompare` -> `Compare`, `UFVCondition` -> `Condition`). Unreal's instanced UObjects (fragments, conditions, effects) become plain C# classes serialized polymorphically.
- The ontology tree (Game -> Interface, Gameplay, Presentation, three children per node) and the rule of three carry over: at most 3 of anything the player sees (HUD sections, hub pages, menu entries, dialogue choices plus cancel).

## Reuse and licences

- Find the root cause, design and plan before adding code. Adding code is not always the answer; prefer removing and simplifying. No helper for every inconvenience.
- Reuse .NET, the libraries above and open-source projects before writing our own. Stride (MIT) is the main source: copy and adapt its code where it fits, keep its copyright header in copied files and list it in `THIRD-PARTY-NOTICES.md`.

## Conventions

- Idiomatic C#: file-scoped namespaces, one main type per file named after it.
- Entities are Arch-first (owner, 2026-11-20): components are plain data structs, behaviour lives in systems, one per feature. Systems add lifecycle hooks for their components to `EntityLifecycle` (`Game.Lifecycle`: attach runs in the editor and the game, for looks from data; activate only while playing; deactivate and detach in reverse), and talk through events, plain structs sent to and handled on `Game.Events` (`EventBus`, dispatched after each group of systems). No string-addressed messages except across worlds or for deferred calls.
- Data-driven, composition over inheritance, SOLID/KISS/YAGNI, open/closed.
- Interface what is worth interfacing: services and the dependencies tests substitute (`IFactDatabase`).
- Don't nest calls: store a call's result in a variable before passing it to another call. Only simple getters and properties may be passed inline.
- Don't chain ternaries; use `if`/`else` or a `switch`.
- Minimal comments: a one-sentence `<summary>` on a type; on a member only when its name or logic is unclear.
- Warnings are errors.

## Build and test

- `dotnet build FlickerVoidNGN.slnx` and `dotnet test --solution FlickerVoidNGN.slnx` (Microsoft Testing Platform, xUnit v3); the same for `Projects/FlickerVoid/FlickerVoid.slnx` (run from its folder, which has its own `global.json`) and `Samples/FlickerVoid.Samples.slnx`.
- CI runs both on Windows and Linux for every pull request, creates and runs a project from the template, then publishes the samples with NativeAOT and runs them (the window sample on SDL's dummy video driver, the textured mesh and scene viewer samples on lavapipe, under Xvfb on Linux). Arch components must be registered with `ArrayRegistry.Add<T>()` (scene components are, through `SceneSpawner.Register`), or NativeAOT builds fail when the first entity gets them. Cloud sessions can build and test on Linux. The editor viewport (Avalonia GPU interop) needs a real GPU: lavapipe exports no semaphores, so it is tested on the owner's PC.
- Graphics tests render on whatever GPU is present and skip when none is. In CI they run on lavapipe, the software Vulkan driver: on Linux from `mesa-vulkan-drivers` plus `vulkan-validationlayers`, on Windows through `jakoch/install-vulkan-sdk-action`, with `LP_PERF=no_rast_linear`, because llvmpipe's linear rasterizer reads push constants past 16 bytes as zero, and on Linux under `xvfb-run` so the swapchain tests get a window.
- Unit tests use xUnit v3, NSubstitute for mocking and AwesomeAssertions (the Apache-2.0 fork of FluentAssertions) for assertions; test projects named `*.Tests` get all three from `Directory.Build.props`. The class under test is created by a builder in a separate `<Class>TestsBuilder.cs` file in the same folder (`GameTestsBuilder.cs` for `GameTests.cs`).
- Work is done TDD. Tests are written first, and serve as the Design Spec for the code.

## Versions

- The engine's version is `Version` in `Source/Directory.Build.props`: `0.<roadmap stage>.<patch>`. Bump it in the pull request that completes a stage (minor) or fixes a released one (patch). When main gets a version without a tag, CI tags the commit `v<Version>` and packs the engine modules as NuGet packages (a workflow artifact).
- Projects reference the engine's projects, not its packages, so every project build compiles the current engine. Packages are for an installed engine without source.
