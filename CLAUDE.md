# FlickerVoidNGN

A C# engine built for fast prototyping and easy development.

The target game is a third-person narrative RPG/adventure with an orthographic 2.5D look: 3D scenes with hand-drawn textures and a 2D feel. It is neither 2D-first nor photoreal. Lighting is the most important part of the look. The game is player-paced: no decay timers or forced timings.

Plan, decisions and roadmap: `Docs/Plan.md`.

## Stack

- .NET 10 LTS; NativeAOT for release builds, so runtime libraries set `IsAotCompatible` and avoid reflection (use source generators, such as System.Text.Json source generation).
- Silk.NET for windowing, input and graphics bindings. Vulkan 1.3 only, on Windows and Linux (Direct3D 12 was dropped: Vulkan has the RTX features, and one API halves the graphics code and its tests).
- HLSL shaders, compiled by DXC to SPIR-V. The `ShaderCompiler` tool (`Source/Tools/ShaderCompiler`) wraps DXC for the builder and for tests and depends on nothing; games never compile shaders, they load the builder's `.spv` files through `ShaderLibrary`.
- Arch for entities and components, BepuPhysics for physics, SharpGLTF for glTF.
- Avalonia for the editor, with its GPU interop for the viewport. The editor is four projects in `Source/Editor`: `Shell` (`FlickerVoid.Editor`, the program: AXAML views, the viewport's GPU interop, the material editor window, the project picker and Play), `Core` (`FlickerVoid.Editor.Core`: `EditorScene`, the camera, gizmos, picking, overlays, and the inspector and View tab view models), `Assets` (`FlickerVoid.Editor.Assets`: the asset browser, material documents and unsaved content) and `Persistence` (`FlickerVoid.Editor.Persistence`: project files, building, creating and launching games). Only the shell uses Avalonia, so the others run headless in tests; it maps Avalonia keys and mouse to Core's `ViewportInput` (`ViewportKeys`). The editor follows MVVM: AXAML views with compiled bindings, view models on CommunityToolkit.Mvvm (`[ObservableProperty]` partial properties), and testable models (`EditorCamera`, `EditorScene`) under them. Its viewport draws the world through `SceneRenderer` with editor passes added after post-processing (`SkyPass`, a sky-like gradient where the scene left the view empty and hidden in the game view, then `GridPass`, thin faint lines that only suggest the ground, then `OverlayPass` for gizmos, selection shapes and the icons of lights and other invisible entities, built each frame by `OverlayBuilder`). When the selection is a camera, its live view is drawn in the viewport's bottom right corner, framed (`ViewportViewModel.GetPreviewCamera`; `ViewportRenderer` draws it with a second `SceneRenderer` without the editor passes and copies it in with `ICommandList.CopyTexture`'s destination offset). Picking is on the CPU, so it needs no GPU: icons in screen space first (`EditorIcons`), then model triangles (`ScenePicker`). Editor icons are Material Symbols (Apache-2.0) PNGs in `Source/Editor/Core/Icons` and the editor's shaders are in `Source/Editor/Core/Shaders`; the shell builds them into `Content/Engine/EditorIcons` and `Content/Engine/Editor`. The gizmo's move and rotate handles follow the world's axes or the entity's own (`GizmoSpace`; scale handles always follow its own), and it snaps when the viewport toolbar turns it on (`GizmoSnap`): moves put the dragged axis on a grid, turns go in steps of degrees, scaling in steps of the starting scale. Shift+A over the viewport opens the Add menu, `EntityPreset`s grouped by `EntityPresetGroup`. The shell's look lives in `Themes/EditorTheme.axaml`: Fluent recoloured with a warm dark palette, compact sizes, icon buttons (Material Icons path data in `MaterialIcons`) coloured by what they do (`play`, `save`, `delete`, `bake`), and the viewport bars; the main window extends into its title bar (`ExtendClientAreaToDecorationsHint`), so the logo, title, tool buttons and Play share one bar with the system's caption buttons, and the empty bar behind them (`WindowDecorationProperties.ElementRole` TitleBar) drags the window; numbers in the inspector are `DragNumberBox`es, dragged sideways or typed after a click, with a bar in the axis colour on X, Y and Z. Every edit of the editor's world goes through `EditorScene` (`SetComponent`, `AddComponent`, `RemoveComponent`, `AddEntity`, `DuplicateEntity` (Ctrl+D), `DestroyEntity`), which raises `Edited` and leaves the scene unsaved (`IsUnsaved`, `UnsavedChanged`) until it is saved or another scene opens; the inspector, gizmo drags and Bake Probes' file names all use it, and nothing else writes to that world. Material and mood edits are held unsaved by `UnsavedContent`, the `IContentManager` the editor runs on, which serves them to whatever loads through it (the viewport shows them at once) until they are saved or discarded; a file that changes on disk while it has unsaved edits keeps them, and the status bar says so. The title shows `*` while anything is unsaved, and the unsaved assets prompt (`UnsavedAssetsDialog`: Save, Discard, Cancel) lists the scene and the assets before the editor closes, and the scene before another scene opens (`MainWindowViewModel.AskUnsaved`). The Material Editor is its own window (`MaterialEditorWindow`): a browser of the content folder's `.fvmat` files, a field per parameter the scene shader declares (the inspector's field view models over `IEditableValue`), edits held unsaved with Save and Discard, and a sphere or cube preview rendered by `MaterialPreview` on its own device and read back into a bitmap, so it needs no GPU interop. The inspector has no per-component code: it lists the components registered for scene files (`ISceneSpawner.Components`, each a `SceneComponent` with its source-generated `JsonTypeInfo`) and picks a field view model by property type, refined by optional attributes (`[Color]` and `[ContentFile]`, which suggests the content files a field may name, from Runtime; `[Range]` from DataAnnotations); string arrays such as `MeshRenderer.Materials` are edited item by item (`ListFieldViewModel`). The View tab beside the inspector edits the viewport's `LightingMood` the same way (`ViewSettingsViewModel`, a field per mood property): the mood file the open scene names (a `SceneMood` component on an entity, from Rendering; the Add menu's Scene Mood), or else a `.fvmood` opened in the asset browser, or else the default mood, unsaved; the viewport draws with that file and the View tab edits it (`MoodDocument`, its edits held by `UnsavedContent` like a material's). The mood includes its `Tonemapper`: post-processing ends with a tonemapper picked by enum (`Uncharted2` Hable filmic by default, `Aces`, `None`) and switched in `Post.hlsl`'s `Tonemap`; a new one is an enum value and a case there. Bake Probes (`SceneProbes`) bakes every irradiance volume with that mood on a device of its own into its probes file in the content folder (a volume without one gets `<Scene>.<Volume>.fvprobes` beside the scene), and the viewport's probe cache reloads it. Save (Ctrl+S) writes the world back into the open scene file (`SceneLoader.Save` over `ISceneSpawner.Capture`): one entity per line, components the world left unchanged kept as the file wrote them and changed ones written in full; comments are lost. Save Assets (Ctrl+Shift+S) and Discard Assets save or drop every unsaved material and mood. The asset browser under the viewport (`AssetBrowserViewModel` over `AssetCatalog`) shows the content folder's tree and the selected folder's subfolders and files as tiles (`Items`, an icon and colour per `AssetKind`, `AssetKindLooks`), hidden dot-files skipped, with a kind filter (by extension) and a search through everything below the selected folder; tiles and tree folders have context menus (open, rename, delete, new), and a tile dropped on a folder moves there (`MoveTo`); opening a scene replaces the open one (`EditorScene.Open`, `SceneLoader.Unload`), opening a material shows it in the material editor, and a model dragged into the viewport becomes a mesh entity named after it, on the mesh or ground under the mouse (`AssetDrag`, `ViewportViewModel.DropModel`). It creates folders, scenes, materials and moods (named `New Scene` and so on, numbered when taken, naming the content folder's schema), and renames and deletes files and folders, all through `IContentManager` (`Write`, `CreateFolder`, `Move`, `Delete`). Data assets open in the Data tab (`DataDocument` over `DataTypes.ReadAsset`/`WriteAsset`, edits held by `UnsavedContent`): a form generated from the asset's metadata (`DataObjectViewModel`: a field per value, a section per nested object, and a `DataListViewModel` per list of objects such as fragments, whose Add offers each `$type` registered for the element type); the browser's New Data Asset and New Table submenus list the registered types (`AssetChoice`). Tables open there too (`TableDocument`, `TableViewModel`): a form per row, rows added, renamed and removed, and CSV export and import for spreadsheets (`TableCsv`: a `name` column, then one per property, strings as written and other values as JSON). Every save goes through `IContentManager.Write`, which in a development build also writes the source file the build manifest maps it to, so editor changes outlive the next build.
- One codebase for Windows and Linux. When something is OS-specific, build it for Windows first and leave a `// TODO(Linux): ...` note on the Linux side.

## Layout

- `Source/Engine/<Module>/FlickerVoid.Engine.<Module>.csproj`, `Source/Editor/<Module>/FlickerVoid.Editor.<Module>.csproj` and `Source/Tools/<Module>/FlickerVoid.Tools.<Module>.csproj`, tests in the same folders under `Tests/` (`FlickerVoid.Engine.<Module>.Tests.csproj` and so on). Namespaces follow folders.
- Inside a module, folders group by what code is about: Graphics and Graphics.Vulkan by resource kind (`Devices`, `Buffers`, `Textures`, `Samplers`, `Pipelines`, `Commands`, `Presentation`, `Resources`/`Descriptors`); Rendering by feature (`Cameras`, `Meshes`, `Materials`, `Lighting`, `Shadows`, `GlobalIllumination`, `PostProcessing`, `Extraction`, `Pipeline`); Runtime and Platform likewise (`Loop`, `Windowing`, `Native`).
- Rendering never reads the Arch world while drawing: an `IRenderExtractor` (default `WorldExtractor`) copies it into a plain `RenderScene`, then `SceneRenderer` runs its `RenderPipeline` of `IRenderPass`es (Prepare all, write the frame data, Execute all) over a shared `RenderContext`. New rendering features are new passes added, inserted or replaced in the pipeline, not branches in `SceneRenderer`.
- Engine file types carry `fv` extensions: scenes `.fvscene`, materials `.fvmat`, lighting moods `.fvmood`, shader descriptions `.fvshader` (built shader parameters `.fvparams`), baked models `.fvmodel`, baked probes `.fvprobes`, entity templates `.fventity`, data assets `.fvdata`, data tables `.fvtable`, flow graphs `.fvflow`, projects `.fvproject`. Text ones are JSON with a `$schema`; standard formats keep theirs (`.glb`, `.png`, `.hlsl`, `.dds`, `.spv`).
- Content is built by the `Builder` tool (`Source/Tools/Builder`, `FlickerVoid.Tools.Builder`), a command-line program the editor runs too. A game lists its source folders as `<FlickerVoidContent Include="Content" />`, and `Source/Tools/Builder/FlickerVoid.Tools.Builder.targets` (imported by `Samples/Directory.Build.targets`) builds them into `Content/` in the output and publish folders. The shaders of the engine modules a project references (`Source/Engine/<Module>/Shaders`) are built into `Content/Engine/<Module>`, where `ShaderLibrary.ForEngine` finds them, so test projects that draw import the targets too. A shader is `Name.hlsl` plus `Name.fvshader` listing its entry points and stages, built into `Name.EntryPoint.spv`; HLSL uses real `#include`s. Images (PNG, JPEG, TGA, BMP) become sRGB BC7 `Name.dds` files with full mip chains (`DdsImage`); content names a texture by its source image (`Paper.png`) and `TextureLibrary` loads the `.dds`. A shader may declare material parameters in its `.fvshader` (`parameters`: name, `float` or `color`, default, optional limits), written to `Name.fvparams`; `Name.fvmat` files set them by name (`MeshRenderer.Materials`, one per mesh part), and `MaterialLayout` packs them tightly in declared order for the shader's `LoadMaterial`. glTF models (`.glb`, `.gltf` with its buffers and images) are baked by `ModelImporter` into `Name.fvmodel` (`ModelFile`: mesh parts, BC7 textures, baked animation clips); content names them by source (`Room.glb`) and `MeshLibrary` loads the `.fvmodel`, so the runtime never reads glTF or decodes images. Each file goes through the `IAssetImporter` registered for its extension, or is copied; a content-hash cache (`.build-cache.json`) skips files whose source, dependencies and importer version haven't changed.
- Entity templates (`.fventity`, `EntityTemplates`, `SceneLoader.Templates` and a game service) are an entity's components and values, optionally over a `base` template, like a Blueprint carrying looks and data. A scene entity names one with `template` and keeps only what differs from it: `SceneLoader` expands templates before spawning or patching (`JsonMerge.Merge`, property by property) and saves only the differences (`JsonMerge.Diff`); a template that changes on disk patches every loaded scene using it. Game code spawns one with `EntityTemplates.Spawn`, placed at a transform and started.
- Data assets (`.fvdata`: one object, like an Unreal Data Asset with instanced objects) and data tables (`.fvtable`: named rows of one type, like a Data Table) hold C# types registered on `Game.Data` (`DataTypes`): modules add the source-generated context describing their types (`AddResolver`), then `Register<T>(name)` for asset types, `RegisterRow<T>(name)` for row types and `RegisterDerived<TBase, TDerived>(name)` for fragments, conditions and effects. A file names its type in `type`; a polymorphic value names its derived type in `$type`, added through a resolver modifier, so reading stays reflection-free. `DataAssets` (a game service from `SceneHost`) loads them, one object per file until it changes on disk, lists every asset of a type (`LoadAll<T>`) and finds a definition by its tag id (`Find<T>`), and the `data` and `table` schemas list every registered type. References to data files are content paths (`[ContentFile(".fvdata")]`).
- Input is read as actions, like Enhanced Input: an input map (`InputMap`, a data asset of type `inputMap`, registered by `game.AddInput()`) names each action by a tag and binds keys, mouse buttons or the mouse's movement, each adding its `Value` (so W, A, S and D make a move vector). `InputActions` (a frame system and service, added by `SceneHost` before the game's systems, with an empty map until the game sets one) gives each action's value and whether it is held, pressed or released, and sends `InputActionEvent`s; systems read actions by tag, never keys. `GestureTracker` follows a press, hold, mash, hover or automatic `Gesture` of one action.
- Characters are point and click (owner, 2026-11-21: point and click with the orthographic view; no third-person camera). The `Characters` module (over Physics) has `CharacterMover` (scene component `characterMover`: speed, turn speed, arrive distance) and `CharacterMovementSystem` (`game.AddCharacters()`, after `AddPhysics` when the game has physics): a `MoveCommand` event sends a character walking to a point (a `Destination` component while it walks), it walks straight there turning to face its way (characters face +Z, the front of a glTF model) and standing on the ground a physics ray finds, and sends `ArrivedEvent`; `StopCommand` stops it. Paths around obstacles come with `Ai`. A click becomes a world ray with `CameraView.GetRay` (Rendering, over `Ray.FromViewProjection` in Runtime's `Geometry`, which the editor's picking shares) and meets the world through `IPhysicsSystem.RayCast`, which returns the nearest body's entity, point and normal.
- Flow graphs (`.fvflow`, the `Flow` module over Runtime, like the Unreal Flow plugin) are scripted sequences for story, quests and dialogue: nodes linked output pin to input pin. A node derives from `FlowNode<TOut>` (one input, `In`) or `FlowNode<TIn, TOut>`, whose enums are its pins (`FlowInput`, `FlowOutput`, `NoPins`, or its own nested `Out`), so it triggers `context.Trigger(Out.True)` with no pin strings; files name pins by enum name, and a `FlowRun` resolves the links to pin indices once, throwing for a missing node or pin. Each node type is registered on `Game.Data` with `RegisterDerived<FlowNode, T>` and named by `$type`; nodes without inputs run as the run starts. The editor opens a `.fvflow` from the asset browser (New Flow creates one with a start node) in a `FlowEditorWindow`: a canvas over `FlowGraphViewModel` (Core: nodes laid out in fixed rows so pins sit where `FlowPinViewModel.Point` says, wires drawn by `FlowWires`; right-click to add a node of any registered type, drag nodes, drag pin to pin to wire, right-click a pin to unwire, Delete removes) beside the selected node's form (`DataObjectViewModel`, its id and place hidden); edits are held by `UnsavedContent` through `FlowDocument` and written with `FlowGraphs.Write`. `SceneHost` adds flow to every game and serves `FlowGraphs`. `game.AddFlow()` registers the core nodes (`start`, `finish`, `branch`, `applyEffects`, `waitForConditions`) and the `flow` schema; `FlowGraphs` reads a file and starts a `FlowRun` against a `ConditionContext`. Nodes are shared data: a run keeps the active nodes, passes signals along links in order, tells active nodes when a fact changes, and stops a trigger that loops. Gameplay's condition and effect types (`fact`, `group`) are registered by `Game` itself, so any data file can hold condition sets and effect lists.
- Content hot-reloads: `ContentWatcher` (a frame system) reports files that changed on disk to `IContentManager.NotifyChanged`, which forgets the cached JSON and raises `Changed` with the full path. Anything that caches what it loaded from a file (the mesh, texture and probe caches, `SceneLoader`, `LightingMoodDirector`) listens to `Changed` and drops or patches what it holds; the scene loader and mood director keep the last good version when an edited text file can't be read. In a development build the targets also write `Content/.content-build` (the builder and the source folders) and copy the build caches beside it; `ContentWatcher` then starts the builder in watch mode (`ContentBuildProcess`, `--watch`), so saving a source file rebuilds it into the game's content folder and the reload follows. Published games have neither file. Text content has JSON Schemas generated from the same source-generated metadata that reads it (`JsonSchemas`): modules add theirs to `Game.Schemas` (`scene` from every registered component, `mood` from Rendering), and a development run writes them into each source content folder's `.schemas` (`ContentWatcher`), which the builder skips. Content files name theirs with `"$schema": "../.schemas/scene.schema.json"`; root file types carry a `Schema` property for it.
- Modules arrive with their roadmap stage (`Docs/Plan.md`). Don't create empty projects, folders or classes ahead of their stage.
- Samples that show a stage's gate: `Samples/<Name>/FlickerVoid.Samples.<Name>.csproj`, in their own solution `Samples/FlickerVoid.Samples.slnx`.
- Dependencies only point down: Editor -> Rendering -> Graphics -> Runtime -> Gameplay; inside the editor, Shell -> Assets, Persistence and Core, Assets -> Core, and Core -> Rendering, while Persistence references nothing; Tools' Builder -> ShaderCompiler and Rendering. Engine source projects never reference Tools or Editor; engine tests may (`Tests/Engine/Graphics` compiles shaders with the ShaderCompiler tool); Physics and Platform (window and input) -> Runtime; `Hosting` -> Platform, Rendering and Graphics.Vulkan runs a game in a window (`SceneHost`: device, game with rendering, the built content, the `--scene`/`--mood`/`--frames`/`--validation` options read by `HostOptions`, and `SceneRenderSystem` drawing last with an optional `IFrameOverlay`; without `--mood` it draws with the scene's `SceneMood`), which the template's launcher and the samples use. `Gameplay` holds the engine-neutral rules (definitions, fragments, tags, facts, conditions, effects, scales) and depends on no other engine module; conditions read entities through `IEntityView`, which Runtime implements over Arch (`WorldEntityView`). Game builds never contain editor code. `Debug` (Dear ImGui panels for development: engine stats and rendering switches, and `DebugWindow` for a project's own panels, as in Cog) depends on Hosting, and `DebugUi` is a frame overlay; samples and projects reference it and show it with `--debug` or F1, and release builds leave it out.
- Users' projects live in `Documents/FlickerVoid/<Project>`. The demo project is FlickerVoid, in this repo at `Projects/FlickerVoid`: `Source/<Module>/FlickerVoid.<Module>.csproj`, tests in `Tests/<Module>/FlickerVoid.<Module>.Tests.csproj`, folders following the ontology tree (`Gameplay/Protagonist/Identity/Social`). Game-specific rules (social, quests) live there, not in the engine.
- Benchmarks of the engine's hot code paths (BenchmarkDotNet) are in `Benchmarks/FlickerVoid.Engine.Benchmarks.csproj`, one class per path, grouped by module (`Rendering/WorldExtractorBenchmarks.cs`). Run them with `dotnet run --project Benchmarks -c Release -- --filter '*'`; `--profiler EP` adds a CPU trace of each benchmark (`.speedscope.json`, opened in speedscope.app) showing where the time goes. The Benchmarks workflow runs them on every push and pull request: a results table, a comparison with main and charts (`.github/scripts/BenchmarkCharts.cs`, Mermaid: this run per benchmark, and main's history) in the run's summary, the traces as an artifact, and a commit comment when a benchmark gets 50% slower than main.
- The engine solution `FlickerVoidNGN.slnx` holds only engine modules, their tests and the benchmarks. Each project is its own solution (`<Project>.slnx`) with an Engine solution folder listing the engine's module projects (references, not copies), so engine classes can be seen and edited from the project and the changes land in the engine repository. A project finds the engine through `$(FlickerVoidEngine)`, set by its `Directory.Build.props` from the `FLICKERVOID_ENGINE` environment variable (falling back to the repository the project sits in), and imports the engine's `Directory.Build.props` and `Directory.Packages.props`.
- A project is opened in the editor through its `<Name>.fvproject` file (JSON: `game`, the launcher's C# project; `startupScene`), like a `.uproject`: the editor (`FlickerVoid.Editor <file>.fvproject`) builds the game first (`EditorProject`, `DotnetProjectBuilder`), which builds its content, then loads the built game's code (`GameCode`: the `IGameModule`s of the launcher and the project assemblies it references, in a load context of their own that shares the editor's engine assemblies; loaded once per run, since Arch keeps every component type it has seen) and adds them to the editor's game, so scenes know the project's components, then opens the built content and the startup scene; the build manifest beside the content names the source folders, which the asset browser lists and every save writes, while `ContentWatcher` runs the builder over them in watch mode (`EditorScene.Poll`). The template's launcher lists the project's `Content` folder. A project registers its components, systems and hooks in an `IGameModule` (Runtime), which its launcher adds to `SceneHost.Game` before running. Play (F5, `ScenePlayer`) runs the project's built game (`EditorProject.Program`) on the open scene as the viewport shows it, without saving anything: the world and the viewport's mood are written to `.play/<Scene>.fvscene` and `.play/<Scene>.fvmood` in the built content folder and the game gets `--scene` and `--mood` (`ProcessGameLauncher`); the game's watcher sees the editor's builder already holds the manifest (`ContentWatchLock`), so only one builder runs. Started without a project or content folder, the editor shows the project picker (`ProjectPickerWindow`): the projects in `Documents/FlickerVoid`, Browse for a `.fvproject`, or Create a new one from the template (`TemplateProjectCreator`, which installs it from `FLICKERVOID_ENGINE`); the build runs off the UI thread and the editor window replaces the picker.
- New projects come from the `dotnet new` template in `Templates/Project` (`dotnet new install ./Templates/Project`, then `dotnet new flickervoid -n <Name> --engine <engine folder>`); the editor creates projects through the same template. `--engine` only fills the solution's Engine folder; builds find the engine through `FLICKERVOID_ENGINE`, with no fallback in the project's build files; the editor (`DotnetCli`) uses the variable or else the engine folder it runs from, and sets it on every `dotnet` it starts. Keep the template in step with `Projects/FlickerVoid`'s build files and the engine's module list.

## Porting from Unreal

- Read the Unreal source (FVFramework, FVGameplay and the plugins) before porting, and port its behaviour and its tests. Never write an API from memory.
- C# types drop the Unreal prefixes (`EFVCompare` -> `Compare`, `UFVCondition` -> `Condition`). Unreal's instanced UObjects (fragments, conditions, effects) become plain C# classes serialized polymorphically.
- The ontology tree (Game -> Interface, Gameplay, Presentation, three children per node) and the rule of three carry over: at most 3 of anything the player sees (HUD sections, hub pages, menu entries, dialogue choices plus cancel).

## Reuse and licences

- Find the root cause, design and plan before adding code. Adding code is not always the answer; prefer removing and simplifying. No helper for every inconvenience.
- Reuse .NET, the libraries above and open-source projects before writing our own. Stride (MIT) is the main source: copy and adapt its code where it fits, keep its copyright header in copied files and list it in `THIRD-PARTY-NOTICES.md`.

## Conventions

- Idiomatic C#: file-scoped namespaces, one main type per file named after it.
- Entities are Arch-first (owner, 2026-11-20): components are plain data structs, behaviour lives in systems, one per feature. Systems add lifecycle hooks for their components to `EntityLifecycle` (`Game.Lifecycle`: attach runs in the editor and the game, for looks from data; activate only while playing; deactivate and detach in reverse), and talk through events, plain structs sent to and handled on `Game.Events` (`EventBus`, dispatched after each group of systems). No string-addressed messages except across worlds or for deferred calls.
- Data-driven, composition over inheritance, SOLID/KISS/YAGNI, open/closed.
- Interface what is worth interfacing: services and the dependencies tests substitute (`IFactDatabase`).
- Don't nest calls: store a call's result in a variable before passing it to another call. Only simple getters and properties may be passed inline.
- Don't chain ternaries; use `if`/`else` or a `switch`.
- Minimal comments: a one-sentence `<summary>` on a type; on a member only when its name or logic is unclear.
- Warnings are errors.

## Build and test

- `dotnet build FlickerVoidNGN.slnx` and `dotnet test --solution FlickerVoidNGN.slnx` (Microsoft Testing Platform, xUnit v3); the same for `Projects/FlickerVoid/FlickerVoid.slnx` (run from its folder, which has its own `global.json`) and `Samples/FlickerVoid.Samples.slnx`.
- CI runs both on Windows and Linux for every pull request, creates and runs a project from the template, then publishes the samples with NativeAOT and runs them (the window sample on SDL's dummy video driver, the textured mesh and scene viewer samples on lavapipe, under Xvfb on Linux). Arch components must be registered with `ArrayRegistry.Add<T>()` (scene components are, through `SceneSpawner.Register`), or NativeAOT builds fail when the first entity gets them. Cloud sessions can build and test on Linux. The editor viewport (Avalonia GPU interop) needs a real GPU: lavapipe exports no semaphores, so it is tested on the owner's PC.
- Graphics tests render on whatever GPU is present and skip when none is. In CI they run on lavapipe, the software Vulkan driver: on Linux from `mesa-vulkan-drivers` plus `vulkan-validationlayers`, on Windows through `jakoch/install-vulkan-sdk-action`, with `LP_PERF=no_rast_linear`, because llvmpipe's linear rasterizer reads push constants past 16 bytes as zero, and on Linux under `xvfb-run` so the swapchain tests get a window.
- Unit tests use xUnit v3, NSubstitute for mocking and AwesomeAssertions (the Apache-2.0 fork of FluentAssertions) for assertions; test projects named `*.Tests` get all three from `Directory.Build.props`. The class under test is created by a builder in a separate `<Class>TestsBuilder.cs` file in the same folder (`GameTestsBuilder.cs` for `GameTests.cs`).
- Work is done TDD. Tests are written first, and serve as the Design Spec for the code.

## Versions

- The engine's version is `Version` in `Source/Directory.Build.props`: `0.<roadmap stage>.<patch>`. Bump it in the pull request that completes a stage (minor) or fixes a released one (patch). When main gets a version without a tag, CI tags the commit `v<Version>` and packs the engine modules as NuGet packages (a workflow artifact).
- Projects reference the engine's projects, not its packages, so every project build compiles the current engine. Packages are for an installed engine without source.
