# The editor

- Avalonia for the editor, with its GPU interop for the viewport. The editor is four projects in `Source/Editor`: `Shell` (`FlickerVoid.Editor`, the program: AXAML views, the viewport's GPU interop, the material editor window, the project picker and Play), `Core` (`FlickerVoid.Editor.Core`: `EditorScene`, the camera, gizmos, picking, overlays, and the inspector and View tab view models), `Assets` (`FlickerVoid.Editor.Assets`: the asset browser, material documents and unsaved content) and `Persistence` (`FlickerVoid.Editor.Persistence`: project files, building, creating and launching games). Only the shell uses Avalonia, so the others run headless in tests; it maps Avalonia keys and mouse to Core's `ViewportInput` (`ViewportKeys`). The editor follows MVVM: AXAML views with compiled bindings, view models on CommunityToolkit.Mvvm (`[ObservableProperty]` partial properties), and testable models (`EditorCamera`, `EditorScene`) under them. Its viewport draws the world through `SceneRenderer` with editor passes added after post-processing (`SkyPass`, a sky-like gradient where the scene left the view empty and hidden in the game view, then `GridPass`, thin faint lines that only suggest the ground, then `OverlayPass` for gizmos, selection shapes and the icons of lights and other invisible entities, built each frame by `OverlayBuilder`). When the selection is a camera, its live view is drawn in the viewport's bottom right corner, framed (`ViewportViewModel.GetPreviewCamera`; `ViewportRenderer` draws it with a second `SceneRenderer` without the editor passes and copies it in with `ICommandList.CopyTexture`'s destination offset). Picking is on the CPU, so it needs no GPU: icons in screen space first (`EditorIcons`; camera cues show an outlined camera with a play badge, `CameraCue.png`, unlike cameras), then model triangles (`ScenePicker`). Editor icons are Material Symbols (Apache-2.0) PNGs in `Source/Editor/Core/Icons` and the editor's shaders are in `Source/Editor/Core/Shaders`; the shell builds them into `Content/Engine/EditorIcons` and `Content/Engine/Editor`. F frames the selection, or the whole scene, keeping the view's direction (`ViewportViewModel.FrameSelected`, `EditorCamera.Frame`); a right-click without a drag opens the viewport's options. The gizmo's move and rotate handles follow the world's axes or the entity's own (`GizmoSpace`; scale handles always follow its own), and it snaps when the viewport toolbar turns it on (`GizmoSnap`): moves put the dragged axis on a grid, turns go in steps of degrees, scaling in steps of the starting scale. Menus are shared controls (`Shell/Controls`): view models offer `MenuChoice`s (Core `Menus`: name, group, icon name from `MaterialIcons.Find`, key, action) and each menu picks its own `MenuGrouping` (none, separators or submenus); Shift+A opens the searchable Add menu (`SearchMenu` over `SearchMenuViewModel`, via `EditorMenus.AddChoices`) over the viewport (`EntityPreset`s), the asset browser (`NewChoices`) and the flow graph, and a right-click opens a plain options menu (`EditorMenus.ShowOptions`, `MenuNode`s through the `ChoiceMenuItem` theme); menus scroll past `EditorMenuMaxHeight`. `SearchBox` is the one search field (rounded, magnifying glass, clear button), bound to whatever it searches. The side panel resizes and splits the scene outliner and the Entity tab over the Inspector, View and Data tabs. The scene outliner (`SceneTreeViewModel`) shows folders and entities with icons (`SceneIcons`, by component): an entity's folder is `EntityData.Folder` in the scene file (`folder`, held as the Runtime component `EntityFolder` and saved back); choosing a folder selects everything in it, and the selection holds many entities (`EditorSelection.Entities`, with `Selected` for the inspector and gizmo, which moves the rest with it); folders are created (filing the selection), renamed, removed and dragged into each other there. Entities nest under other entities (`EntityData.Parent` in the scene file, `parent`, the parent's name, held as the Runtime component `EntityParent` and saved back; `EditorScene.SetParent`, undone as a `ParentStep`, `GetParent`, `GetChildren`, `GetDescendants`): a child follows its parent's moves, in the editor and the game, through Runtime's `TransformHierarchy` (a game service `Game` updates after each fixed step and before each frame, and `EditorScene` after each edit), which keeps each child's place in its parent's space (`Attachment`, never saved) while transforms stay in world space for every other system. The outliner lists only entities at the top; an entity with nested ones has a reveal button that shows its whole tree under it, the nested names in blue (or every one, with the outliner's reveal toggle; a selection made elsewhere reveals and expands what holds it), an entity dropped on another nests under it and one filed in a folder comes off its parent; the Entity tab beside it (`EntityTreeViewModel`, `EntityTreeView`) shows the selection's whole tree from its top entity, everything nested shown; both views set their tree's items themselves while syncing, as a new item list makes a `TreeView` drop its selection and that must not read as a choice. Each row (`SceneTreeRow`) has an eye that hides the entity and what is nested under it in the editor's views (`EditorScene.SetHidden`, `ShowAll`: Rendering's `Hidden` tag, which `WorldExtractor`, picking, icons and trigger shapes skip; neither saved nor undone, and the game shows them), and the outliner's bar hides or shows the selection and shows everything. The shell's look lives in `Themes/EditorTheme.axaml`: Fluent recoloured with a warm dark palette, never flat: the window, bars, headers and tabs are the frame (`EditorFrameBrush`, the kitchen palette's green), and every content area (viewport, trees, lists, forms, the flow canvas) sits in a `Border.well` sunk into it (the darker panel colour, slightly rounded, an inner shadow), with text inputs darker still; compact sizes, icon buttons (Material Icons path data in `MaterialIcons`) coloured by what they do (`play`, `save`, `delete`, `bake`), and the viewport bars; the main window extends into its title bar (`ExtendClientAreaToDecorationsHint`), so the logo, title, tool buttons and Play share one bar with the system's caption buttons, and the empty bar behind them (`WindowDecorationProperties.ElementRole` TitleBar) drags the window; numbers in the inspector are `DragNumberBox`es, dragged sideways or typed after a click, with a bar in the axis colour on X, Y and Z and a yellow one (`EditorValueBrush`) on every other number. Every edit of the editor's world goes through `EditorScene` (`SetComponent`, `AddComponent`, `RemoveComponent`, `AddEntity`, `DuplicateEntity` (Ctrl+D), `DestroyEntity`), which raises `Edited` and leaves the scene unsaved (`IsUnsaved`, `UnsavedChanged`) until it is saved or another scene opens; the inspector, gizmo drags and Bake Probes' file names all use it, and nothing else writes to that world. Undo and redo (Core `Undo`: `UndoHistory` of `UndoStep`s, one history per document, owner 2026-11-22) store state, never inverse operations: each `EditorScene` edit records the touched component's JSON before and after (`ComponentStep`), a folder change (`FolderStep`) or the whole entity added or deleted (`EntityStep`), all keyed by entity name, since handles die with their entity, and applied back through the same edit methods while `IsApplying` keeps them from recording; `BeginGroup`/`EndGroup` make a gizmo drag, a duplicate or delete of the selection, outliner filing, a number box drag (`DragNumberBox.DragStartedEvent`/`DragCompletedEvent`) or a flow node drag one step, merging repeated edits of the same thing (`TryMerge`); histories keep at most 200 steps and 64 MB. `UnsavedContent.Edit` records each asset edit as the whole file before and after (`ContentStep`, a history per file from `GetHistory`, kept through saves, cleared by a discard, a change on disk or a move or delete), and an undo that reaches the file on disk leaves it saved; `Restored` tells the material editor, the View and Data tabs, flow and texture windows to open the file again. `UndoShortcuts` gives each window Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z over its document (the main window's View or Data tab's file while the keyboard is there, else the scene), the top bar's Undo and Redo buttons (`MainWindowViewModel.UndoCommand`, `RedoCommand`, over the history the keyboard is in, `SidePanelFocused`) do the same, the viewport passes Ctrl shortcuts on to its window, and the viewport's options name the next steps. Selection, camera moves and asset browser file operations are not undone. Material and mood edits are held unsaved by `UnsavedContent`, the `IContentManager` the editor runs on, which serves them to whatever loads through it (the viewport shows them at once) until they are saved or discarded; a file that changes on disk while it has unsaved edits keeps them, and the status bar says so. The title shows `*` while anything is unsaved, and the unsaved assets prompt (`UnsavedAssetsDialog`: Save, Discard, Cancel) lists the scene and the assets before the editor closes, and the scene before another scene opens (`MainWindowViewModel.AskUnsaved`). The Material Editor is its own window (`MaterialEditorWindow`): a browser of the content folder's `.fvmat` files, a field per parameter the scene shader declares (the inspector's field view models over `IEditableValue`), edits held unsaved with Save and Discard, and a sphere or cube preview rendered by `MaterialPreview` on its own device over the editor's content (its meshes and material in a hidden `.material-preview` folder, so the material's textures are found) and read back into a bitmap, so it needs no GPU interop. The inspector has no per-component code: it lists the components registered for scene files (`ISceneSpawner.Components`, each a `SceneComponent` with its source-generated `JsonTypeInfo`) and picks a field view model by property type, refined by optional attributes; Add Component opens the searchable Add menu of the missing components grouped by module with icons (`ComponentChoices`) (`[Color]` and `[ContentFile]` from Runtime; `[Range]` from DataAnnotations); string arrays such as `MeshRenderer.Materials` are edited item by item (`ListFieldViewModel`); other lists and arrays (a shot's keys, an area's tags) get a field per item (`CollectionFieldViewModel` over `ElementValue`s) and nested objects (a cue's transition) a field per property (`ObjectFieldViewModel` over `MemberValue`s), with a kind to switch for a polymorphic one (a body's collider), every edit writing a copy back through the owner (`EditableJson`) so undo keeps the old value; each field's row (`FieldRow` in the shell's `App.axaml`) puts nested ones under their label; tags are edited as their names (`TagProperty`). A string naming a content file (`[ContentFile]`) is picked like Unreal's asset picker (`AssetFieldViewModel`, and each item of such a list, over `AssetPickerViewModel`; `AssetPickerView` in the shell): the current file with its kind's icon opens a popup listing the files with the field's extensions, read again on each opening, with a search box (Enter takes the first match) and None when the value may be empty; the button beside it raises `AssetPickerView.OpenRequestedEvent`, and the main window (for its own fields and the flow editor's) shows the file in the asset browser (`AssetBrowserViewModel.Reveal`) and opens it as a double-click would (`MainWindowViewModel.OpenContentFile`). The View tab beside the inspector edits the viewport's `LightingMood` the same way (`ViewSettingsViewModel`, a field per mood property): the mood file the open scene names (a `SceneMood` component on an entity, from Rendering; the Add menu's Scene Mood), or else a `.fvmood` opened in the asset browser, or else the default mood, unsaved; the viewport draws with that file and the View tab edits it (`MoodDocument`, its edits held by `UnsavedContent` like a material's). The mood includes its `Tonemapper`: post-processing ends with a tonemapper picked by enum (`Uncharted2` Hable filmic by default, `Aces`, `None`) and switched in `Post.hlsl`'s `Tonemap`; a new one is an enum value and a case there. Bake Probes (`SceneProbes`) bakes every irradiance volume with that mood on a device of its own into its probes file in the content folder (a volume without one gets `<Scene>.<Volume>.fvprobes` beside the scene), and the viewport's probe cache reloads it. Save (Ctrl+S) writes the world back into the open scene file (`SceneLoader.Save` over `ISceneSpawner.Capture`): one entity per line, components the world left unchanged kept as the file wrote them and changed ones written in full; comments are lost. Save Assets (Ctrl+Shift+S) and Discard Assets save or drop every unsaved material and mood. The asset browser under the viewport (`AssetBrowserViewModel` over `AssetCatalog`) shows the content folder's tree under its search box, a narrow column of type filters and the selected folder's subfolders and files as tiles (`Items`, an icon and colour per type, `AssetTypeLooks`); each type of file is one `AssetType` in `AssetTypes` (its name, extensions, icon, colour and what New writes, `AssetNew`), so a new type of file is one entry there, and the main window opens each type in its editor from one table (`MainWindowViewModel.CreateOpeners`), hidden dot-files skipped; the search looks through everything below the selected folder; it has no buttons: tiles and tree folders have context menus (open, rename, duplicate, delete, new, import, reimport, up, refresh), and a tile dropped on a folder moves there (`MoveTo`); files from outside the editor, dropped on the browser or picked with Import, are copied into the folder they land on or the selected one (`Import`), their sources remembered in the content folder's hidden `.imports` file (`ImportSources`, kept through renames, moves and deletes; the builder skips hidden files and Blender files), so Reimport copies a changed source again; opening a scene replaces the open one (`EditorScene.Open`, `SceneLoader.Unload`), opening a material shows it in the material editor, and a model dragged into the viewport becomes a mesh entity named after it, on the mesh or ground under the mouse (`AssetDrag`, `ViewportViewModel.DropModel`). It creates folders and the files of every type New makes (scenes, vehicles, materials, moods, canvases and flow graphs; a new vehicle is a car on four wheels), named `New Scene` and so on, numbered when taken, naming the content folder's schema, and renames and deletes files and folders, all through `IContentManager` (`Write`, `CreateFolder`, `Move`, `Delete`). A file owns the files in its folder named after it (`AssetCatalog`): a creation (`AssetType.IsCreation`, such as `Van.fvvehicle`) every `Van.<anything>` (its `.blend`, models and paintings), any other file those named after its whole name (an image's `Paper.png.fvtexture` settings), the shortest name winning, so a group's files all start with its name. The browser shows a group as its owner's tile, framed in its type's colour, whose arrow lists the owned files after it (`ToggleExpanded`; `AssetEntry.Owned`, `Owner`, `Label`); renaming, moving and duplicating any of its tiles act on the whole group (Duplicate, Ctrl+D, numbers the copy from 2, a name none of the group's files takes), while Delete takes the whole group from the owner's tile and one file from an owned tile; a type filter lists a matching owned file on its own, `Reveal` expands the group of an owned file, and asset pickers list owned files too (`ContentFileFinder`). With a project open it also shows the project's `Source` folder as a second root, Code (`AssetCatalog.ForCode`, paths under `/Code`, build output skipped, `.cs` files opened in the IDE), where it only writes: New > Flow > Flow Node asks for a name and a code folder (`FlowNodePrompt`: the selected code folder, or the one whose path ends most like the selected content folder's, or the first holding a C# project) and `FlowNodeSource` writes the class there in its project's namespace and adds it to the project's JSON context; it is in flow graphs after the next build. Data assets open in the Data tab (`DataDocument` over `DataTypes.ReadAsset`/`WriteAsset`, edits held by `UnsavedContent`): a form generated from the asset's metadata (`DataObjectViewModel`: a field per value, a section per nested object, and a `DataListViewModel` per list of objects such as fragments, whose Add offers each `$type` registered for the element type); the browser's New Data Asset and New Table submenus list the registered types (`AssetChoice`). Tables open there too (`TableDocument`, `TableViewModel`): a form per row, rows added, renamed and removed, and CSV export and import for spreadsheets (`TableCsv`: a `name` column, then one per property, strings as written and other values as JSON). Every save goes through `IContentManager.Write`, which in a development build also writes the source file the build manifest maps it to, so editor changes outlive the next build.
- Whole trees: duplicating an entity copies everything nested under it (taken names numbered, save ids given free ones, the copies nested under their copied parents), deleting removes the tree deepest first, and the viewport skips selected entities nested under other selected ones. F2 or the outliner's Rename renames an entity (`EditorScene.RenameEntity`, undone as a `RenameStep`), refusing a taken name and rewriting every `[EntityReference]` that names it. Save as Template (the outliner's menu) writes the entity as `Templates/<Name>.fventity` and has it start from it, and the inspector's Template row picks the template an entity starts from (`EditorScene.SetTemplate`, a `TemplateStep`). Nested entities are not part of templates yet.
