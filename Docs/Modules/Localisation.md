# Localisation

- Every text the player sees goes through a key (owner, 2026-11-27: localisation is important). Its shape is the one the VE engine report found (section 21): a key, the text, and a note of context for the translator. The languages are decided when the story is further along.
- A text is a `LocalizedText` (Gameplay `Localization`): `key` (dot-separated like a tag, `Quest.Cellar.Name`; one key is one text), `text` (as written, in the language the game is written in) and `note` (who says it, where it shows, what it means). Content writes it as an object: `"name": { "key": "Item.CellarKey.Name", "text": "Cellar key", "note": "A brass key the innkeeper lost." }`. The engine's player-facing fields are texts: a definition's display name and descriptions (`DisplayInfo`), a condition set's failure reason, dialogue lines, choices and barks, quest objectives, ability failure messages, map layer and marker labels and check modifier labels; the events and views that carry them (`DialogueLine`, `DialogueChoice`, `BarkEvent`, `OfferView`, `MarkerView`, `CheckLine`, `AbilityFailedEvent`) carry the text, not a string, so the interface turns it into the chosen language as it draws, and again when the language changes. Ids, tags, fact descriptions for designers and debug descriptions stay strings.
- The text as written stays beside its key in the content (as Unreal's `FText` keeps its source string), so writers read and edit lines where they are; translations sit apart, by key, in string tables. An empty text needs no key. A text written in code is a `LocalizedText` too, with its key and note, declared to the localizer (`TextLocalizer.Declare`) by the module that writes it, so the content check and translators know it: the engine's `CheckSystem.RollLabel` (`Check.Roll`, declared by `AddAttributes`), a game's interface labels. A fallback the engine makes up, such as an attribute's tag name or a condition's description in place of a failure reason, has none and shows as it is.
- String tables (`StringTable`, `.fvstrings`, schema `strings`) are the translations, in the content's `Localization` folder (`TextLocalizer.Folder`): each names its `culture` (`"culture": "pl"`) and translates texts by their keys, wherever they are written: `"texts": { "Hub.Close": { "text": "Zamknij", "source": "Close" } }`, where `source` is the text the translation was made from, so a text rewritten since can be told out of date, and `note` is the translator's own. Several tables of one culture add up. Texts as written are never in tables: they stay where they are written, in content or code.
- `TextLocalizer` (Runtime `Localization`, `Game.Localization`, also a service) shows texts: `Get(LocalizedText)` gives the chosen culture's translation of its key, or the text as written where there is none (an empty translation counts as none). The culture is the `loc.Culture` console variable (saved in the settings file; empty, the default, shows texts as written), so the language can be switched while the game runs, as VE's can. `Changed` is raised when the culture changes or a table changes on disk. `SceneHost` loads the tables from the game's content (`Load`); a game without content, as in tests, shows texts as written.
- The content check (`ContentCheck`) reads every text at any depth and every table, with the declared texts written in code (reported at `ContentCheck.CodePath`), and reports a text without a key, a key given to two different texts (the same text may share a key, such as two offers' `Take`), a translation of a key no text has, and a table that names no culture. Translations missing or out of date are work for translators, not problems.
- In the editor a text is a nested object in the inspector (key, text, note), as any other object value.
- Not yet: generating keys in the editor as a line is written, a gather tool writing the texts to translate (with their notes and what changed since the last translation) into a culture's table, plural and gendered forms, and fonts for scripts beyond Latin.
