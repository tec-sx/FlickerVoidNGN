# Scenes, entities and data

- Greyboxes (owner, 2026-11-23: a modular greybox editor, most basic first) lay out levels before their models exist: a `greybox` component (Runtime `Greyboxes`: size, solid, swaps, swap) is a grey box standing on its entity, made from its size rather than loaded (`GreyboxMesh`, a mesh name the mesh library and the editor's picking turn into a box with texture coordinates in metres), solid ones get a static box from physics while playing (so paths are built over them), and `Swaps` lists models (from Blender) that may stand in its place, the one shown chosen by `Swap` (0 shows the box). The editor's Add menu has a Greybox group (box, wall, floor); stairs are a floor turned into a ramp.
- Solids (Runtime `Solids`, milestone 1 of the creation tools) are the shapes the creators greybox with: a `SolidMesh` is points and faces (points listed counter-clockwise seen from outside) that must close, each edge shared by exactly two faces running opposite ways, or it is refused. `Box` and `Cylinder` make the first ones, `Transform` moves, turns and mirrors (a mirror turns the faces back so they still face out), and `Triangulate` gives flat-shaded triangles in the engine's winding with texture coordinates in metres, as greyboxes have. Files hold a solid as `{ "points": [[x, y, z], ...], "faces": [[0, 1, 2, 3], ...] }` (`SolidMeshJsonConverter`, with its own schema), and one that isn't closed can't be read, the reason being the error's message.
- Entity templates (`.fventity`, `EntityTemplates`, `SceneLoader.Templates` and a game service) are an entity's components and values, optionally over a `base` template, like a Blueprint carrying looks and data. A scene entity names one with `template` and keeps only what differs from it: `SceneLoader` expands templates before spawning or patching (`JsonMerge.Merge`, property by property) and saves only the differences (`JsonMerge.Diff`); a template that changes on disk patches every loaded scene using it. Game code spawns one with `EntityTemplates.Spawn`, placed at a transform and started. Entity classes are typed handles over entities (design doc "Entities, data assets and flow graphs"): a `readonly partial struct` marked `[EntityClass]` (Runtime `Entities`, optionally naming its `Template`) declares a `partial ref` property per component (`public partial ref Lockable Lock { get; }`), and the `EntityClassGenerator` (`Generators`, FVG001 to FVG003 for a property that isn't a component by ref, a class without components, or one nested or generic) implements it over `World.Get` and `IEntityClass<TSelf>`: a constructor over a world and an entity, `Is`, `TryGet`, `From`, the `Query` of every entity with its components and its `Components`, so `door.Lock.IsLocked` reads the entity's own component with no copy. `EntityTemplates.Spawn<TClass>` spawns one from its template, with the components neither the template nor the transform give at their defaults. Classes never derive from each other; logic only they need goes in a system that queries them.
- Data assets (`.fvdata`: one object, like an Unreal Data Asset with instanced objects) and data tables (`.fvtable`: named rows of one type, like a Data Table) hold C# types registered on `Game.Data` (`DataTypes`): modules add the source-generated context describing their types (`AddResolver`), then `Register<T>(name)` for asset types, `RegisterRow<T>(name)` for row types and `RegisterDerived<TBase, TDerived>(name)` for fragments, conditions and effects. A file names its type in `type`; a polymorphic value names its derived type in `$type`, added through a resolver modifier, so reading stays reflection-free. `DataAssets` (a game service from `SceneHost`) loads them, one object per file until it changes on disk, lists every asset of a type (`LoadAll<T>`) and finds a definition by its tag id (`Find<T>`), and the `data` and `table` schemas list every registered type. References to data files are content paths (`[ContentFile(".fvdata")]`).
- Scene travel (`Runtime/Scenes`; `game.AddSceneTravel(scenes)`, which `SceneHost` adds as `Travel` and starts the game with): `SceneTravel` (a service) unloads the scene loaded and loads the next, standing its `traveller`s at the entry entity named (`Travel(scene, entry)` between ticks; `Request` from effects and flow nodes, run before the next tick), and raises `Leaving`, `Arriving` and `Arrived`. Flow has the `travel` node and effect.
- Names link entities (parents, shot targets, cues), so the editor keeps them unique and `SceneLoader` warns of two entities sharing a name or a save id. String properties that name an entity are marked `[EntityReference]` (Runtime `Components`), so renames rewrite them (`EntityReferences`) and the content check finds those naming nothing. `TransformHierarchy` keeps the parent each child found while it lives under that name, and looks names up only for children without one; a parent can also be given as the entity (`NestedUnder`, set by `TransformHierarchy.Attach` with the child's place in the parent's space), as spawned parts are, and wins over a name.
- The game loop: `Game.Defer(action)` runs an action before the next tick, outside every system (travel and loads replace entities systems use); `Game.Pause(reason)` and `Resume(reason)` hold the game paused while any reason is held (fixed systems stop, frames go on with `GameTime.Paused`, so the interface runs); `Game.Random` (`GameRandom`) is the game's one source of chance, saved with it (`random`), which modules roll from unless a test gives them their own.
