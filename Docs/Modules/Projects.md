# Projects

- Users' projects live in `Documents/FlickerVoid/<Project>`: `Source/<Module>/<Project>.<Module>.csproj`, tests in `Tests/<Module>/<Project>.<Module>.Tests.csproj`, folders following the ontology tree (`Gameplay/Protagonist/Identity/Social`). Projects can sit in any folder, as the project picker remembers them. The game itself is Bleeders, in its own repository (`tec-sx/Bleeders`), which builds against the engine `FLICKERVOID_ENGINE` names like any project (one shared engine clone, never a copy per project); game-specific rules (social, quests), content and their tests live there, not in the engine.
- The engine solution `FlickerVoidNGN.slnx` holds only engine modules, their tests and the benchmarks. Each project is its own solution (`<Project>.slnx`) with an Engine solution folder listing the engine's module projects (references, not copies), so engine classes can be seen and edited from the project and the changes land in the engine repository. A project finds the engine through `$(FlickerVoidEngine)`, set by its `Directory.Build.props` from the `FLICKERVOID_ENGINE` environment variable (falling back to the repository the project sits in), and imports the engine's `Directory.Build.props` and `Directory.Packages.props`.
- A project is opened in the editor through its `<Name>.fvproject` file (JSON: `game`, the launcher's C# project; `startupScene`; `splash`, an image beside it that the editor's splash shows while the project builds; without one it shows the editor's own, a four-pointed star in a dreamy void, `Projects/DefaultSplash.jpg` in the shell), like a `.uproject`: the editor (`FlickerVoid.Editor <file>.fvproject`) builds the game first (`EditorProject`, `DotnetProjectBuilder`), which builds its content, then loads the built game's code (`GameCode`: the `IGameModule`s of the launcher and the project assemblies it references, in a collectible load context of their own that shares the editor's engine assemblies, read from copies in memory so the build can overwrite the files) and adds them to the editor's game, so scenes know the project's components, then opens the built content and the startup scene; Compile (Ctrl+Alt+F11, after Unreal's Live Coding; `GameCompiler`) builds the game again off the UI thread, loads the new code and `EditorScene.Reload`s with it: a new game spawns the open scene as captured (`SceneLoader.Load` with contents in place of the file), so unsaved edits survive, the selection follows by name, undo steps are dropped (they hold the old code's components), the asset browser lists the new data types (`ListDataTypes`), and the old code is unloaded; a failed build or a scene the new code can't spawn (a component gone) leaves the old game in place. Arch's component registry is static, so unloaded code is never fully collected: each reload leaks a little until the editor restarts; Open in Visual Studio, beside Compile in the title bar, opens the solution beside the project file (`EditorProject.Solution`: the one named after the project, else the first) in the newest Visual Studio `vswhere` finds, else in what the system opens it with (`VisualStudio`); the build manifest beside the content names the source folders, which the asset browser lists and every save writes, while `ContentWatcher` runs the builder over them in watch mode (`EditorScene.Poll`). The template's launcher lists the project's `Content` folder and adds vehicles to its game (`AddVehicles`). A project registers its components, systems and hooks in an `IGameModule` (Runtime), which its launcher adds to `SceneHost.Game` before running. Play (F5, `ScenePlayer`) runs the project's built game (`EditorProject.Program`) on the open scene as the viewport shows it, without saving anything: the world and the viewport's mood are written to `.play/<Scene>.fvscene` and `.play/<Scene>.fvmood` in the built content folder and the game gets `--scene` and `--mood` (`ProcessGameLauncher`); the game's watcher sees the editor's builder already holds the manifest (`ContentWatchLock`), so only one builder runs. Started without a project or content folder, the editor shows the project picker (`ProjectPickerWindow`): the projects in `Documents/FlickerVoid` and every project opened before from anywhere (`RecentProjects`, the newest ten in `FlickerVoid/Editor/RecentProjects.json` under local application data, written whenever a project opens, from the picker or the command line), the last one selected, Browse for a `.fvproject`, or Create a new one from the template (`TemplateProjectCreator`, which installs it from `FLICKERVOID_ENGINE`). Opening one covers the picker with a 16:9 splash, after Unreal's (`SplashWindow` over `SplashViewModel`: the project's `splash` image, a thin progress bar and one status line), while the build runs off the UI thread: `DotnetProjectBuilder` first asks MSBuild for the program and the projects the build builds (`-t:GenerateRestoreGraphFile` with `-getProperty:TargetPath`), then `BuildProgressReader` follows the build's minimal output line by line (`DotnetCli.Run`'s line callback, reported through `IProjectBuilder`'s `IProgress<BuildProgress>`): MSBuild prints `Name -> output` as each project finishes, so the bar counts the projects built and the line names those whose references are all built, what builds now, or shows the build's other lines (restore, content, errors) as they are. The editor window then replaces the picker and its splash; anything thrown while opening (a failed build, a bad project file, the template) closes the splash and shows the exception's log over the picker (`ProjectFailureWindow`; the build's output when the build failed), to copy or close. A project given on the command line, as Open Project's restart is, still builds before any window shows. The Open Project button before Save shows the same picker over the editor; the project it opens replaces the open one after the unsaved prompt by starting the editor again on its `.fvproject` (`MainWindow.OnClosed`, through `ProcessGameLauncher`), as Unreal does, since a run loads only one game's code.
- New projects come from the `dotnet new` template in `Templates/Project` (`dotnet new install ./Templates/Project`, then `dotnet new flickervoid -n <Name> --engine <engine folder>`); the editor creates projects through the same template. `--engine` only fills the solution's Engine folder; builds find the engine through `FLICKERVOID_ENGINE`, with no fallback in the project's build files; the editor (`DotnetCli`) uses the variable or else the engine folder it runs from, and sets it on every `dotnet` it starts. Keep the template in step with Bleeders' build files and the engine's module list.
