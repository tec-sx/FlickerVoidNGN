# Inventory

- Inventory (the `Inventory` module over Runtime, ported from FVInventorySystem; `game.AddInventory(settings)`) carries items. An `ItemDefinition` data asset (type `item`: category, weight, cells across and down, stack size where 0 is unlimited and 1 makes every unit its own entry, quest item, and fragments such as `usable` (use conditions, effects, consumed on use), `charges` (uses per unit) and `value`) is held in `ItemStack`s (id, item, quantity, immutable `ItemInstanceData` records such as `ChargesLeft` and `Stolen`; stacks with data never merge). An `inventory` component names its starting items and money and whether carry limits apply (off for chests and shops); while playing it is an `ActiveInventory`. `InventorySystem` (a service) does the rest: weight and cell limits from `InventorySettings` plus the bonus the game grants (units fill existing stacks for free, each new stack claims the item's cells, key item categories take neither), story items that ignore limits, removal from plain stacks first, use with the owner as instigator and target (a charge first, so a partly used unit becomes its own stack), transfers (plain units move as far as they fit, stacks with data whole; optionally marked stolen), `Receive` for what is picked up, money, and finding items by tag. Changes are sent as `ItemChangedEvent`, `StackChangedEvent`, `ItemUsedEvent`, `MoneyChangedEvent` and `CapacityChangedEvent`. A `pickup` component (item, quantity, destroyed when empty) is an `ActivePickup` stack while playing; `PickupSystem` (a service) takes it into a picker's inventory as far as it fits or uses it where it lies (`PickedUpEvent`, `UsedInPlaceEvent`, after which an empty pickup goes). The inventory conditions (`hasItem`, `hasItemWithTag`, `hasMoney`) and effects (`giveItem`, ignoring limits, `takeItem`, `giveMoney`, `takeMoney`) look at their `Subject`, the instigator by default, and find `InventorySystem` and `DataAssets` in the context's services; `pickUp` and `useInPlace` are effects for an interaction offer, with the interactor picking up or using the interactable, so Inventory needs no Interaction. Outfits: an `equipment` component (starting items by slot, linked to carried stacks, and whether only carried items can be worn) is an `ActiveEquipment` while playing, and `EquipmentSystem` (a service) wears `equippable` items (slots, blocked slots, granted tags, equip conditions, mesh) one per slot, taking off what conflicts; worn items' granted tags are added to the wearer's `OwnedTags` (keeping tags others gave), a worn stack that leaves the inventory comes off (`EquipmentChangedEvent`), and worn `container`s (bags) add cells and weight allowance. `InventorySystem` reads `ActiveEquipment` for that: worn stacks are removed and used last, never transferred, and a worn bag stays on while its room is needed. The `isWearing` condition checks an item or a granted tag, and `giveItem` can wear what it gives. Loot: a `LootTableDefinition` (type `lootTable`: up to three entries, each an item or a nested table with a quantity range, a chance and conditions, plus a money range) is rolled by `LootSystem` (a service, with the `Random` given to `AddInventory` so tests seed it; nested tables roll their quantity of times, at most eight deep, and a table leading back to itself is skipped), into an inventory as far as it fits (`GiveLoot`, the `giveLoot` effect), or once into a `lootable` container (table, owner, rolled). Inside the engine the `Inventory` component's name meets the `FlickerVoid.Engine.Inventory` namespace, so engine code outside its folder names it `Inventories.Inventory`.
