# Content

- Content is built by the `Builder` tool (`Source/Tools/Builder`, `FlickerVoid.Tools.Builder`), a command-line program the editor runs too. A game lists its source folders as `<FlickerVoidContent Include="Content" />`, and `Source/Tools/Builder/FlickerVoid.Tools.Builder.targets` (imported by `Samples/Directory.Build.targets`) builds them into `Content/` in the output and publish folders, leaving out hidden files and Blender files with their backups (`Van.blend`, `Van.blend1`), which sit beside the creations made from them. The shaders of the engine modules a project references (`Source/Engine/<Module>/Shaders`) are built into `Content/Engine/<Module>`, where `ShaderLibrary.ForEngine` finds them, so test projects that draw import the targets too. A shader is `Name.hlsl` plus `Name.fvshader` listing its entry points and stages, built into `Name.EntryPoint.spv`; HLSL uses real `#include`s. Images (PNG, JPEG, TGA, BMP) become sRGB `Name.dds` files with full mip chains (`DdsImage`), as their optional settings beside them say (`Paper.png.fvtexture`, `TextureSettings`: BC7 or uncompressed, a size limit the image is halved to, tint, crop; applied by `TextureEdits`, read by `TextureImporter` as a dependency, and owned by the image in the asset browser, so they are moved, duplicated and deleted with it); content names a texture by its source image (`Paper.png`) and `TextureLibrary` loads the `.dds`. Everything is painted on a canvas: a mood names a `.fvcanvas` (`CanvasFile`: image, tiling up the screen at an orthographic height of 10, intensity (how far its texture strays from its average colour; the canvas is the image's only grain), tint; sampled through its mips so small windows don't alias), which `PostProcessPass` lays flat under the scene, moved and scaled with an orthographic camera's pans and zooms and still when it turns (`CanvasView`), and shows unlit where nothing is painted and through paint that is not thick impasto. Double-clicking an image or a canvas in the asset browser opens the texture editor (`TextureEditorWindow` over `TextureEditorViewModel`: a field per setting, held unsaved by `UnsavedContent`, and a CPU preview of what the build makes of the image or of the canvas repeated by its tiling). A shader may declare material parameters in its `.fvshader` (`parameters`: name, `float` or `color`, default, optional limits), written to `Name.fvparams`; `Name.fvmat` files set them by name (`MeshRenderer.Materials`, one per mesh part), and `MaterialLayout` packs them tightly in declared order for the shader's `LoadMaterial`. glTF models (`.glb`, `.gltf` with its buffers and images) are baked by `ModelImporter` into `Name.fvmodel` (`ModelFile`: mesh parts, BC7 textures, baked animation clips); content names them by source (`Room.glb`) and `MeshLibrary` loads the `.fvmodel`, so the runtime never reads glTF or decodes images. Each file goes through the `IAssetImporter` registered for its extension, or is copied; a content-hash cache (`.build-cache.json`) skips files whose source, dependencies and importer version haven't changed.
- Content hot-reloads: `ContentWatcher` (a frame system) reports files that changed on disk to `IContentManager.NotifyChanged`, which forgets the cached JSON and raises `Changed` with the full path. Anything that caches what it loaded from a file (the mesh, texture and probe caches, `SceneLoader`, `MoodSystem`) listens to `Changed` and drops or patches what it holds; the scene loader and mood system keep the last good version when an edited text file can't be read. In a development build the targets also write `Content/.content-build` (the builder and the source folders) and copy the build caches beside it; `ContentWatcher` then starts the builder in watch mode (`ContentBuildProcess`, `--watch`), so saving a source file rebuilds it into the game's content folder and the reload follows. Published games have neither file. Text content has JSON Schemas generated from the same source-generated metadata that reads it (`JsonSchemas`): modules add theirs to `Game.Schemas` (`scene` from every registered component, `mood` from Rendering), and a development run writes them into each source content folder's `.schemas` (`ContentWatcher`), which the builder skips. Content files name theirs with `"$schema": "../.schemas/scene.schema.json"`; root file types carry a `Schema` property for it.
- The content check (`ContentCheck.Run(game, folder)`, Runtime `Content`) reads every text file of a source content folder as the game reads it (scenes with their templates expanded, templates, data assets, tables, and the one-value file kinds modules add with `ContentSchemas.AddFile`: moods, environments, materials, canvases, texture settings, flows; comments and trailing commas allowed) and lists `ContentProblem`s: files that can't be read, components no module registers, content files named (`[ContentFile]`, at any depth, polymorphic values included) that the folder lacks or of a kind their property doesn't take, entities named (`parent`, `[EntityReference]`) that their scene lacks, and names or save ids two entities of a scene share. A game's tests run it over the game's content with the launcher's modules (Bleeders' `ContentTests`).
