# Environment

How a place's light changes over the hours of its day (owner, 2026-11-25; issue #199, built task by task).

- Curves (`Curves` in Runtime; for the environment's values over a day, and reusable for anything else drawn over time): a `Curve` is a number over time through `CurveKey`s (`time`, `value`, a `CurveMode` and, for a free key, the slopes `in` and `out` it is arrived at and left at, in value per time), and a `ColorCurve` a color through `ColorKey`s (`time`, `color`, mode), blended channel by channel by the same rules. A key's mode says how the curve travels on to the next key: `Smooth` (the default) eases through the key at the slope between its neighbours, held back (to three times the gentler slope beside it) and flat at a peak or a dip, so the curve never passes above or below its keys; `Linear` is a straight line; `Constant` holds the value until the next key; `Free` uses the key's own slopes (a free color key is smooth). A curve arrives at a smooth key at that key's slope, at a free key at its `in`, and at a linear or constant key straight along the line between the two. Both are immutable and sort their keys by time; of keys sharing a time the later one given is the value there, which makes a step. `Evaluate(time, period)` holds the first and last keys outside them, and with a period (24 for a day; the keys lie from 0 up to it) wraps the time into it, the last key leading on to the first; without keys it gives 0 or black. In files a curve is `{ "keys": [...] }`, read and written by `RuntimeJsonContext`, modes by name and a key's defaults left out.
- Mood values (`Moods` in Rendering): the mood on screen stays one `LightingMood`, and `MoodValues` lists each of its values once, in the mood's own order, as a `MoodValue`: its name as files spell it, the `MoodGroup` it is edited under (`Sun`, `Sky`, `Fog`, `Grade`, `Bloom`, `Tonemapper`, `Canvas`), its `MoodOwner` (`Environment`: the light and air of a place, the grade included, as the owner sets it by hand over the day; `Lens`: bloom, tonemapper, white point and canvas, which the main camera carries) and how to copy and blend it between moods, typed so nothing is boxed: a `MoodNumber` and a `MoodColor` blend evenly, a `MoodDirection` (the sun's) turns rather than shortens, and a `MoodChoice` (tonemapper, canvas) swaps halfway. `LightingMood.Lerp` blends through the table, and a test fails when a value of the mood is missing from it, so a new value is added in two places: the mood and the table.
- Mood overrides: a `.fvmood` file read as a `MoodOverride` (`RenderingJsonContext.Default.MoodOverride`) is only the values the file names, and `Apply` writes those onto whatever mood is under it and leaves the rest alone, a value named at its default included (`"bloom": 0` turns bloom off over a mood that has it). The same file read as a `LightingMood` is still a whole mood with defaults for the rest, which is how scenes, stages and the director read moods until the layers arrive. An override is checked by the mood's own schema and writes back only what it names.
- Environments: a `LightingEnvironment` (a `.fvenv` file, schema `environment`) is a place's light and air over the 24 hours of its day: `numbers` and `colors`, each a curve by the name of the mood value it draws (`{ "numbers": { "exposure": { "keys": [...] } }, "colors": { "fogColor": { "keys": [...] } } }`, key times in hours from 0 up to 24). `Apply(hour, mood)` writes every curve's value at that hour onto the mood and leaves the mood's other values alone, so a value without a curve keeps what lies under it, and one key holds a value all day. Curves wrap around the day (`DayHours`), the last key before midnight leading on to the first after it. Reading a file refuses a curve named for no mood value, for a value of the lens, or of the other kind (a number's curve for a color, or any curve for the sun's direction, which the sky's sun path will turn), so the content check lists a misspelt name.
- The world clock (`WorldClock` in Runtime's `Loop`; `Game.Clock`, also a service): a day and an hour of it (from 0 up to 24, minutes as the fraction, counted in doubles so slow clocks keep time), which pass with the fixed steps at `Speed`, in game hours to a real minute, so it stands still at speed 0 (where every game starts, at hour 0 of day 0) and while the game is paused. `Set(day, hour)` and `Advance(hours)` move it, hours outside the day rolling into the days before or after. The facts follow it: `Time.Hour` (the whole hour, 0 to 23) and `Time.Day` are written when they change, once a whole hour and not every step, and not at all by a clock that never moves, so conditions read the time (`{ "$type": "fact", "fact": "Time.Hour", "compare": "GreaterOrEqual", "value": 20 }`). Writing those facts moves the clock, so fact effects and flows set the time (`Time.Hour` set to 20 is 20:00) or advance it (3 added at 22:30 is 01:00 the next day), and a restored or reset fact database carries it along; while `Time.Held` is above 0 the clock stands still, so a story holds it by adding 1 and lets it go by taking 1 away. Saves keep the facts and, as the `clock` state, the hour to the minute. Nothing expires on the clock: the game stays player-paced, and the clock only moves the light.
